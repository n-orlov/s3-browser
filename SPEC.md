# S3 Browser — Specification

S3 Browser is a desktop Electron application for browsing and editing objects in Amazon S3 (and S3-compatible endpoints). This document describes the product as the code implements it. The tests in `src/__tests__/` and this file are the tracked evidence for its behaviour.

## 1. Process model

The application has three kinds of code, each built by its own script.

| Process | Source | Build output | Role |
| --- | --- | --- | --- |
| Main | `src/main/` (`index.ts`, `ipc/`, `services/`) | `dist/main/` (`tsc -p tsconfig.main.json`) | Owns the window, the AWS SDK clients, the file system and every IPC handler. |
| Preload | `src/preload/index.ts` | `dist/preload/` (`tsc -p tsconfig.preload.json`) | Runs in an isolated context before the page and exposes `window.electronAPI` through `contextBridge`. |
| Renderer | `src/renderer/` (React 19) | `dist/renderer/` (`vite build`) | The user interface. It has no Node.js access and reaches the main process only through `window.electronAPI`. |

- `src/main/index.ts` enforces a single application instance (`app.requestSingleInstanceLock`); a second launch focuses the existing window. On `app.whenReady` it registers `registerCredentialsIpc`, `registerS3Ipc` and `registerAppStateIpc`, then creates one `BrowserWindow` (1200x800, minimum 800x600, no application menu). In development (`NODE_ENV=development`) it loads `http://localhost:5173`; otherwise it loads `dist/renderer/index.html`.
- The preload script exposes `platform` plus three groups of functions, each of which is a thin wrapper around `ipcRenderer.invoke` on one channel from section 2: `appState` (persistence), `aws` (profiles) and `s3` (bucket and object operations). `electronAPI.getObjectMetadata` is an alias for `s3.getObjectMetadata` and invokes the same channel.
- All requests are renderer-initiated request/response calls (`ipcRenderer.invoke` / `ipcMain.handle`). The main process sends no unsolicited events to the renderer.
- The main process holds the selected AWS profile name in memory (set by `aws:set-profile`). Every `s3:*` handler that talks to S3 resolves credentials from that profile. When none is selected, each of them returns `{ success: false, error: 'No AWS profile selected. Please select a profile first.' }` (`s3:delete-prefix` adds `deletedCount: 0, failedCount: 1`), with two exceptions that carry no `error` field:
  - `s3:upload-files` returns `{ success: false, results: [] }`;
  - `s3:delete-files` returns `{ success: false, results: [], deletedCount: 0, failedCount: <number of keys> }`.

## 2. IPC surface

Every channel is registered with `ipcMain.handle` by one of `registerCredentialsIpc` (`src/main/ipc/credentials.ts`), `registerAppStateIpc` (`src/main/ipc/appState.ts`) or `registerS3Ipc` (`src/main/ipc/s3.ts`). The tables below list each channel in the first column in backticks; the unit test `src/__tests__/ipcSpecParity.test.ts` fails when this list differs from the set of registered channels, or when the preload script invokes a channel that is not registered. Arguments are the positional parameters after the implicit event.

Result shapes: `FileOperationResult` is `{ success: boolean; error?: string }`. `ObjectMetadata` is the object's content type, size, last-modified time, ETag, storage class, tags and custom metadata.

| `s3:get-file-size` | `bucket: string`, `key: string` | `{ success; size?: number; error? }` | `{ success: false, error }` |

| `s3:show-file-in-folder` | `filePath: string` | `void`; reveals the file in the system file manager | `undefined` (nothing is revealed) |

| `s3:create-file` | `bucket: string`, `key: string` | `FileOperationResult`; creates an empty object | `{ success: false, error }` |
| `s3:create-folder` | `bucket: string`, `prefix: string` | `FileOperationResult`; creates a zero-byte folder marker object | `{ success: false, error }` |

**Argument validation.** Every handler checks its positional arguments with the helper in `src/main/ipc/validate.ts` before doing any work; the renderer is not trusted. Argument types are: a *bucket name* is a non-empty string of at most 255 characters without `/`; an *object key* is a non-empty string of at most 1024 UTF-8 bytes; a *key prefix* is a string of at most 1024 UTF-8 bytes that may be empty (`prefix` of `s3:delete-prefix` and `s3:create-folder` must be non-empty); a *non-empty string* is at most 4096 characters (profile names, operation ids, local file paths, URLs); `string[]` arguments (`keys`, `filePaths`) are arrays whose items are all object keys, respectively non-empty strings; `newName` is an object key; `content` and `keyOrPrefix` are strings that may be empty. No string may contain a NUL character. Extra arguments are ignored. An argument of the wrong type, a missing argument or a value outside these shapes makes the call resolve (it never rejects) to the *Invalid input* column and the handler body does not run: no S3 request, no filesystem access, no dialog and no shell call. Where the result type has the `{ success, error }` shape the invalid-input result is `{ success: false, error }` with `error` of the form `Invalid argument '<name>': expected <shape>`; otherwise it is the neutral value in the column. The unit test `src/__tests__/ipcValidation.test.ts` holds one row per channel and fails when a registered channel has none.

**Content-read size cap.** `s3:download-content` (text and gzip) and `s3:download-binary-content` (binary, parquet, image) send a HEAD request first and compare `ContentLength` with the cap, 50 MB (`50 * 1024 * 1024` bytes) by default, defined in `src/main/contentLimits.ts` and overridable with the positive-integer environment variable `S3_BROWSER_MAX_CONTENT_BYTES` (bytes). An object above the cap resolves to `{ success: false, error }` where `error` names the limit, and no `GetObject` request is made. The cap applies to the stored size, so a `.gz` object is measured compressed; gunzip output is bounded separately by the same cap (`decompressGzip` in `src/main/services/gzipUtils.ts` passes it as `maxOutputLength`), so a small gzip bomb resolves to `{ success: false, error }` (`Gzip decompression failed: Decompressed content exceeds the maximum size of 50 MB (52428800 bytes).`) instead of exhausting memory. The helper `tryDecompressGzip` falls back to raw text for non-gzip input but rethrows that cap error. A failing HEAD resolves to `{ success: false, error }` with the service message and no download follows.

## 3. Security model

The following is what the code implements; behaviour that is absent is stated as absent.

- **Window isolation.** The `BrowserWindow` is created with `contextIsolation: true`, `nodeIntegration: false` and `sandbox: true`. The renderer cannot `require` Node modules; its only bridge is the `electronAPI` object built in the preload script.
- **Content Security Policy.** `src/renderer/index.html` sets `default-src 'self'; script-src 'self' blob:; style-src 'self' 'unsafe-inline'; img-src 'self' blob:; worker-src blob:; font-src 'self';`. No directive allows a remote (`http:`/`https:`) origin; `src/__tests__/csp.test.ts` parses the policy and fails if one appears. The Monaco editor is bundled from the `monaco-editor` package in `node_modules`: `src/renderer/monacoSetup.ts` passes it to the `@monaco-editor/react` loader (`loader.config({ monaco })`, so no CDN loader path is in effect) and serves its web workers as inlined blob workers built from the same package.
- **Credentials.** AWS credentials are read in the main process from the standard AWS shared config and credentials files and never cross the IPC boundary in clear text. `aws:get-profile-details` masks the access key (first and last four characters), replaces the secret key and session token with `********` and the credential process with `(configured)`. `getCurrentProfileCredentials` is internal to the main process.
- **External links.** `src/main/windowSecurity.ts` (`secureWebContents`, called from `createWindow`) installs a `setWindowOpenHandler` that denies every new window. It passes the requested URL to `shell.openExternal` only when `isExternalOpenAllowed` (`src/main/externalUrlPolicy.ts`) accepts it: the scheme must be `https:` or `mailto:`. `http:`, `file:`, `javascript:`, `data:`, custom protocols and strings that do not parse as a URL are denied and never reach `shell.openExternal`.
- **Navigation.** `secureWebContents` handles `will-navigate` and `will-redirect` on the main window's `webContents` and calls `preventDefault` for any target outside the application origin (the Vite dev server origin in development; the exact `index.html` file URL in production, ignoring query and fragment). Same-origin navigation proceeds. A blocked navigation is not forwarded to the system browser.
- **IPC input.** Every `ipcMain.handle` handler validates the shape of its arguments at runtime through `src/main/ipc/validate.ts` before doing any work, in addition to typing them with TypeScript (section 2, *Argument validation*). A call with an invalid argument resolves to the invalid-input result and the handler body does not run.
- **Errors.** Invalid arguments never reach these paths: they resolve to the invalid-input result of section 2. Every `s3:*` handler whose result has a `success` field catches errors thrown by the AWS SDK or the file system and returns `{ success: false, error }` (for `s3:delete-prefix`, together with `deletedCount: 0, failedCount: 1`), except two that return no `error`: `s3:upload-files` reports per-file failures in `results[].error`, and an error escaping the loop yields `{ success: false, results: [] }`, dropping the results already collected; `s3:delete-files` reports per-key failures in `results[].error`, and an error escaping the loop yields `{ success: false, results: [], deletedCount: 0, failedCount: keys.length }`. `app-state:save` returns `{ success: false, error }` when the state file cannot be written. The `aws:*` handlers, `app-state:load`, `s3:cancel-operation`, `s3:get-parent-prefix`, `s3:get-key-name`, `s3:clear-client`, `s3:show-open-dialog`, `s3:open-downloads-folder` and `s3:show-file-in-folder` have no handler-level catch; an error that reaches them rejects the renderer's `invoke` promise.
- **Downloads.** `s3:download-file` writes into the downloads folder using the final path segment of the key as the file name.
- **Single instance.** A second application instance quits immediately.
- **Workflow permissions.** No workflow in `.github/workflows/` grants a `write` permission (or `write-all`) at workflow top level; a write scope is declared only in the `permissions:` of the job that needs it. A job that holds any write permission must be unreachable from `pull_request` and `pull_request_target`: either its workflow has neither trigger, or the job's `if:` evaluates false for those events (for example `github.event_name == 'push'` or `github.event_name != 'pull_request'`). `src/__tests__/ciWorkflowPermissions.test.ts` enforces this over a directory listing of `.github/workflows/`, so a new workflow file is covered without editing the test, and fails on a condition it cannot parse. Its fixtures prove the checks fire for a top-level `contents: write` and for a pull_request workflow whose write job has no event gate.
- **Packaged files.** electron-builder's `build.files` in `package.json` is `dist/**/*` minus negated patterns for test paths (`__tests__`, `*.test.*`), `e2e`, `coverage`, source maps (`*.map`) and credential-shaped files (`.env*`, `*.pem`, `*.key`, `credentials`, `.npmrc`), so none of them ship in the asar. `src/__tests__/packageConfig.test.ts` fails if any of those exclusions is missing (its fixtures: a `files` list without them, and one with the `*.map` exclusion dropped), and if the release workflow's upload globs do not match the configured targets (`AppImage` to `release/*.AppImage`, `nsis` and `portable` to `release/*.exe`; its fixture uploads `release/*.deb` instead).
- **Repository secret protection.** GitHub secret scanning and secret-scanning push protection are enabled on the `n-orlov/s3-browser` repository (`security_and_analysis.secret_scanning.status` and `security_and_analysis.secret_scanning_push_protection.status` both read `enabled` through the repository API), so a push containing a recognised provider secret is rejected and a committed one raises an alert. This is a repository setting, not code: nothing in the tree enforces it.

## 4. Quality gates

All gates run locally with the `package.json` scripts; CI runs the same commands.

| Script | Command | Gate |
| --- | --- | --- |
| `typecheck` | `tsc -p tsconfig.typecheck.json` | Type-checks `src`, `e2e` and the config files, tests included. |
| `lint` | `eslint . --max-warnings 0` | ESLint at zero warnings: any warning fails the gate. |
| `test:coverage` | `vitest run --coverage` | Unit tests (jsdom) with V8 coverage; thresholds in `vitest.config.ts` are lines 84, functions 83, branches 74, statements 83. `src/main/index.ts` and `src/preload/index.ts` are excluded from coverage. The same run writes, next to the console output: Allure result files from `allure-vitest` into `allure-results-unit/`, a JUnit XML file at `junit/junit.xml`, and the coverage reports in `coverage/` (`coverage-final.json`, which `crap` reads, plus `coverage-summary.json` from the `json-summary` reporter, `lcov.info` and the HTML report). `vitest.config.ts` sets `coverage.reportOnFailure: true`, so a run with a failing test or a suite that fails to load still writes the coverage reports. `allure-results-unit/`, `junit/` and `coverage/` are git-ignored. |

The generator, `@cyclonedx/cyclonedx-npm`, is a devDependency and never appears under `dependencies`. CI uploads the file and the release workflow attaches it (section 5). |
| `build` | `build:renderer`, `build:main`, `build:preload` | Produces `dist/`. |
| `test:e2e:docker` | `./scripts/e2e-docker.sh` | Runs the Playwright Electron suite in `e2e/` against LocalStack, entirely in containers: a LocalStack container plus a Playwright-image container that runs `npm ci`, `npm run build` and `xvfb-run npx playwright test`. Arguments, including `--shard=<i>/<n>`, are forwarded to `playwright test`. Container, network and run names carry `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT`, the shard index (`0` when unsharded) and the shell pid so concurrent runs and shards on one host do not collide. |

**CRAP gate.** `npm run crap` scores every function in `src/main`, `src/preload`, `src/renderer` and `src/shared` (the directories that exist; tests and `.d.ts` files are skipped) as `CRAP = c^2 * (1 - cov)^3 + c`, where `c` is the function's cyclomatic complexity from ESLint's `complexity` rule and `cov` is the fraction of the function's own statements (nested functions excluded) that ran, read from `coverage/coverage-final.json`. A function in a file that has no coverage entry has `cov = 0`. Scoring is `scripts/crap/crapScore.ts`; the CLI is `scripts/crap/crap.ts`. The command prints each offending function as `CRAP <score>  <file>:<qualified name>` and exits non-zero when any function fails; it exits `2` when `coverage/coverage-final.json` is missing, so run `npm run test:coverage` first. A function id is `<file>:<qualified name>` (repeated names in a file get `#2`, `#3`, ... in source order).

- **Limit.** A function not in the baseline fails when its score exceeds `CRAP_MAX` (environment variable, default `30`).
- **Baseline.** `crap-baseline.json` maps function ids to the score they had when the baseline was last written. It lists exactly the functions over `CRAP_MAX` at that time; it is now `{}` (every function scores at most `CRAP_MAX`), and `ratchet:check` keeps it that way (see the ratchet gate). `npm run crap -- --write-baseline` regenerates it from the current code and coverage (honouring `CRAP_MAX`); it is the only supported way to edit it.
- **Shrink-only.** A baselined function fails when its score exceeds its baseline entry, even if the score is below `CRAP_MAX`, so the baseline can only improve: lowering an entry by hand below the live score makes the gate fail, and a function that gets better is locked in by regenerating the baseline. Entries for functions that no longer exist are ignored and reported.

**Ratchet gate.** `.ratchet.json` records the quality ceiling and floors: `maxWarnings` (the lint warning ceiling), `crapBaselineMax` (the allowed number of entries in `crap-baseline.json`) and `coverageThresholds` (`lines`, `functions`, `branches`, `statements`) and `mutationScoreMin` (the mutation break floor, `80`). `maxWarnings` and `crapBaselineMax` are both `0`. `npm run ratchet:check` reads the `--max-warnings` value from the `lint` script in `package.json`, the number of entries in `crap-baseline.json`, the four `coverage.thresholds` from `vitest.config.ts` and `thresholds.break` from `stryker.config.mjs`, prints one `RATCHET` line per regression and exits `1` when `.ratchet.json` records any `maxWarnings` or `crapBaselineMax` other than `0`, when `--max-warnings` is higher than `maxWarnings`, when `crap-baseline.json` has more entries than `crapBaselineMax` (so a function over `CRAP_MAX` can no longer be baselined), when any threshold is lower than its recorded value, when the Stryker `thresholds.break` is lower than `mutationScoreMin`, or when `.ratchet.json` records a `mutationScoreMin` below `80`; it exits `2` when an input is missing or unreadable (a `.ratchet.json` without a numeric `mutationScoreMin` included), and `0` otherwise. `src/__tests__/strykerConfig.test.ts` additionally fails when `thresholds.break` differs from `mutationScoreMin` or when the config's `mutate` list differs from the closed set its header comment names. A coverage threshold or mutation break that is stricter than the record passes and the command prints which `.ratchet.json` entries to tighten; the lint ceiling and the baseline size have no looser or stricter state, so a non-zero `maxWarnings` or `crapBaselineMax` is a violation even when the `lint` script agrees with it. Logic is `scripts/ratchet/ratchetCheck.ts`; the CLI is `scripts/ratchet/ratchet.ts` and runs from the repository root.

**Mutation gate.** `npm run mutation` runs Stryker (`@stryker-mutator/core` with `@stryker-mutator/vitest-runner`, both devDependencies; config in `stryker.config.mjs`) over a closed set of 8 modules: `scripts/crap/crapScore.ts`, `scripts/ratchet/ratchetCheck.ts`, `scripts/summary/jobSummary.ts`, `src/main/ipc/validate.ts`, `src/main/externalUrlPolicy.ts`, `src/main/windowSecurity.ts`, `src/main/services/s3Url.ts` and `src/main/services/gzipUtils.ts` (the `mutate` list is exactly these files and the config's header comment names them). Stryker's `thresholds.break` is `80`, but it judges only the whole run, so `scripts/mutation/mutation.ts` then scores every module of the set on its own from `reports/mutation/mutation.json` and exits `1` when any module scores below the break (score = (Killed + Timeout) / (Killed + Timeout + Survived + NoCoverage); a module missing from the report or without a scoreable mutant also fails), printing one `MUTATION <score>  <module>` line per module and `MUTATION FAIL <module>: ...` per failure; it exits `2` when the report is unreadable. `npm run mutation -- --check-only [report]` skips Stryker and judges an existing report. The pure scoring is `scripts/mutation/mutationCheck.ts`, tested by `src/__tests__/mutationCheck.test.ts`. The HTML (`mutation.html`) and JSON (`mutation.json`) reports are written to the git-ignored `reports/mutation/`; Stryker's sandbox is `.stryker-tmp/` (also git-ignored). A module task runs `npx stryker run --mutate <file>` on its own file only.

The mutation set also runs in CI as `.github/workflows/mutation.yml` (section 5); it is not part of `ci.yml`'s `gate`.

Two repository files adapt Stryker to Vitest 5. `vitest.mutation.config.ts` is `vitest.config.ts` minus the allure setup file and reporters (Stryker's sandbox symlinks `node_modules`, and `allure-vitest/setup` does not resolve from there); the tests and assertions are the same. `scripts/mutation/vitestFileRunner.mjs` registers the test runner `vitest-file`: `@stryker-mutator/vitest-runner` 10 narrows a mutant run with a test-name regex built from space-joined names, which Vitest 5 (it matches `describe > test`) never matches, so every mutant would survive with zero tests run; the wrapper narrows each mutant run to the covering test files instead and otherwise delegates to the vitest runner.

**No fixed sleeps in e2e.** `eslint.config.mjs` applies `no-restricted-syntax` at severity `error` to `e2e/**` with selectors matching every call of `waitForTimeout` (member or bracket form), so `npm run lint` fails on a fixed sleep; tests wait on web-first assertions or `expect.poll` instead, and the rule is never silenced with `eslint-disable`. `src/__tests__/e2eNoFixedSleep.test.ts` lints fixtures through the ESLint Node API and fails if the rule is removed.

`playwright.config.ts` runs one worker, sequentially, with `retries: 0` everywhere (a flaky test fails the run), and forbids `test.only` in CI.

## 5. CI topology

`.github/workflows/ci.yml` defines the `CI` workflow.

- **Triggers.** `push` to `master` or `main`; `pull_request` targeting `master` or `main`; `workflow_dispatch`; and a weekly `schedule` (cron `23 5 * * 1`, Mondays 05:23 UTC, run on the default branch), which runs every job except `publish`. The workflow-level permission is `contents: read` and no job uses secrets; the only job that raises it is `publish` (`contents: write`), which runs only for a push to `master`.
- **Workflow permissions.** `release.yml` declares `contents: write` on each of its three build jobs, not at top level (it triggers only on `release`). The permission rule of section 3 (*Workflow permissions*) applies to every workflow file.
- **Concurrency.** Group `ci-<pull request number or ref>`; a newer run cancels an in-progress run only for pull requests.
- **Runner.** Every job except `gate` and `changes` runs on self-hosted runners labelled `self-hosted, linux, x64, s3-browser`; `gate` and `changes` run no repository code and use GitHub-hosted `ubuntu-latest`. For pull requests each job (and each e2e shard) runs only when the head repository is this repository and both the PR author and the actor are `n-orlov`; pushes and manual dispatches are not gated. `pull_request_target` is not used.
- **Job `quality`** (20-minute timeout): checkout without persisted credentials, Node 22 with npm cache, `npm ci --no-audit --no-fund`, then `npm run typecheck`, `npm run lint`, `npm run test:coverage` and `npm run crap` (both with `if: ${{ !cancelled() }}`, so a red typecheck, lint or test step does not stop the unit and coverage evidence the summary and uploads are built from; a failing test still fails the job), `npm run ratchet:check`, `npm run audit:prod`, `npm run build`, `npm run sbom` (the CycloneDX SBOM of production dependencies, section 4) and four uploads, each in a step with `if: always()` (so a red gate still leaves its evidence), kept 7 days: `coverage/` as `coverage-report`, the Vitest Allure results `allure-results-unit/` as `unit-allure-results`, `junit/junit.xml` as `unit-junit` and `sbom/sbom.cdx.json` as `sbom`. `src/__tests__/sbomWiring.test.ts` fails if the `sbom` script, the devDependency placement of the generator, the `npm run sbom` step, the SHA-pinned SBOM upload with its `if: always()`, or the release attachment is missing (its fixtures remove `if: always()`, the release `files:` entry and the `--omit dev` flag). `src/__tests__/ciReporting.test.ts` fails if `vitest.config.ts` loses the `allure-vitest/reporter` or `junit` reporter or the `json-summary` coverage reporter, or if any of these three uploads loses `if: always()`. - **Job `release-dryrun`** (20-minute timeout, same `runs-on` and the same pull-request owner gate as the other self-hosted jobs, `permissions: contents: read`, no write permission and no publish step): checkout without persisted credentials, Node 20.x with npm cache (the Node major `release.yml` uses), `npm ci`, then a step running `npm run build` and `npx electron-builder --linux -p never`, the commands `release.yml`'s `build-linux` job runs, so a packaging break fails CI instead of the next release. It then uploads `release/*.AppImage` as artifact `release-dryrun-appimage` (`if-no-files-found: error`), kept 7 days. It `needs: changes` and runs when that job's `release` output is `true`, together with the pull-request owner gate: on a push, a scheduled run and a manual dispatch always, on an owner pull request only when a changed file matches `package.json`, `build/**`, `electron-builder*`, `.github/workflows/release.yml`, `vite.config.*` or `tsconfig*.json` (bash globs against the repository-relative path, where `*` also matches `/`, so `build/**` covers every depth and the root-level patterns match only the root file); otherwise it is skipped. It is a `needs` of `gate`, see below. `src/__tests__/ciReleaseDryrun.test.ts` parses both files and fails if the job's `npm ci` / build / package commands differ from `build-linux`'s (its fixture changes the release command), if the upload path or the 7-day retention changes, if the job or the workflow holds a write permission, or if the job gains a publish step. - **Job `changes`** (5-minute timeout, GitHub-hosted `ubuntu-latest`, `contents: read`, the same pull-request owner gate): decides whether `release-dryrun` runs. For a pull request it checks out with full history (no persisted credentials) and matches `git diff --name-only <base sha>...<head sha>` against the `RELEASE_PATHS` list in the step's environment (the six patterns above); for any other event it reports `release=true`. It runs no repository code, only git and shell, so a pull request cannot use it to reach a self-hosted runner. Its single output is `release`.
- **AppImage smoke test.** The last step of `release-dryrun` runs `scripts/smoke-appimage.sh` (default target: the one `release/*.AppImage`). It starts a container from the Playwright image `scripts/e2e-docker.sh` uses (`mcr.microsoft.com/playwright:v<version of @playwright/test in package-lock.json>-noble`), copies the AppImage in with `docker cp` (no host-path bind mount, so it also works from inside another container), extracts it with `--appimage-extract` (no FUSE needed) and launches the extracted `AppRun` under `xvfb-run`. It exits 0 only when a Chromium page titled `S3 Browser` (`S3B_SMOKE_TITLE`) appears and the process is still running 5 s later (`S3B_SMOKE_HOLD`); an early exit, no window within 60 s (`S3B_SMOKE_WAIT`) or a wrong title exits non-zero. The step comes after the electron-builder step and after the artifact upload, so a failing smoke test still leaves the AppImage to download. Electron flags the packaged app gets in the container: `--no-sandbox` because the container runs as root, where Chromium does not start its sandbox, and electron-builder's `AppRun` only adds it when its `unshare -Ur` probe fails, which never happens as root; passing it explicitly keeps the result independent of the runner's kernel; and `--remote-debugging-port=9222` so the script can read the window's title from `/json` without an X11 client tool (the image has none). No other flag is needed (the app starts with software rendering without `--disable-gpu`). `src/__tests__/ciReleaseDryrun.test.ts` asserts the smoke step exists and follows the electron-builder step, and that the script extracts the AppImage and uses `xvfb-run`, the Playwright image and `--no-sandbox`.
- **Job `e2e`** (40-minute timeout, matrix `shard: [1, 2]`, `fail-fast: false`, displayed as `e2e shard <i>/2`): checkout without persisted credentials, Node 22, `./scripts/e2e-docker.sh --shard=<i>/2` with `CI=true`, and, on every outcome (`if: always()`, not only on failure), three uploads kept for 14 days under per-shard names: the Playwright HTML report `playwright-report/` as `e2e-report-<i>`, `test-results/` as `e2e-test-results-<i>` and the Allure results `allure-results/` as `e2e-allure-results-<i>`. `playwright.config.ts` writes them through its reporters `html` (to `playwright-report/`, never opened), `list`, `allure-playwright` (to `allure-results/`, git-ignored) and `json` (to `test-results/results.json`, uploaded with `test-results/`). After the run and before the uploads, a step with `if: always()` runs `node scripts/summary/summary.ts e2e <i>/2`, which appends the shard's passed, failed and skipped counts (from `test-results/results.json`) to `$GITHUB_STEP_SUMMARY`. Each shard runs its own LocalStack and Playwright containers on its own docker network. The `quality` job and both shards have no dependency on each other and run in parallel. `src/__tests__/ciE2eShards.test.ts` fails unless the `e2e` job has exactly the two-shard matrix, passes `--shard`, and names its artifacts per shard. `src/__tests__/ciReporting.test.ts` fails if the `allure-playwright` or `list` reporter is removed from `playwright.config.ts`, or if any of the three e2e uploads loses `if: always()`, the 14-day retention or its per-shard name, or if the shard's summary step is missing or loses `if: always()`.
- **Job `report`** (15-minute timeout, `needs: [quality, e2e]`, same `runs-on` as the other jobs, `permissions: contents: read`, nothing wider): runs on every outcome of its needs. Its condition is `always()` combined with the same pull-request gate as the other jobs (head repository is this repository, author and actor `n-orlov`), because a bare `if: always()` would also run the job for fork pull requests on the self-hosted runners. Steps: checkout of this repository (without persisted credentials, for `scripts/allurerc.mjs`), a second checkout of the `gh-pages` branch into `previous-pages/` (`continue-on-error`: the branch does not exist before the first publish), Node 22, `actions/download-artifact` with pattern `*allure-results*` into `allure-input/` (one sub-directory per artifact: `unit-allure-results`, `e2e-allure-results-1`, `e2e-allure-results-2`), then a step that copies `previous-pages/history.jsonl` (when present) into `allure-report/` and runs `npx --yes allure@3.20.1 generate allure-input/* --config scripts/allurerc.mjs --output allure-report`, then, in a step with `if: always()`, an upload of `allure-report/` as the single artifact `allure-report`, kept 14 days. **CLI choice: Allure 3** (npm package `allure`, pinned to 3.20.1; the results are written by `allure-vitest` and `allure-playwright` 3.x). It accepts several results directories in one `generate`, so unit and e2e results land in one report with an `index.html`; Allure 2 (Java) was not needed. **History:** `scripts/allurerc.mjs` sets `historyPath: ./allure-report/history.jsonl`, `appendHistory: true` and `historyLimit: 50`, so the generated report keeps the previous runs' entries plus this one in `allure-report/history.jsonl` and its trend widgets show them. `src/__tests__/ciReporting.test.ts` also fails if the report job stops seeding that file from `gh-pages` before generating. It fails if the job loses `needs: [quality, e2e]`, its `if: always()`, the same `runs-on`, its read-only permissions, the download of the three Allure artifacts, the `allure generate` step, or the upload's `if: always()`.
- **Job `publish`** (10-minute timeout, `needs: report`, same `runs-on`, `permissions: contents: write`): `if: github.event_name == 'push' && github.ref == 'refs/heads/master'`, so it never runs for a pull request, a `workflow_dispatch` or a push to another branch. It is a job of its own because job permissions cannot be conditional: `report` runs for pull requests and must stay read-only, so the one write permission lives in the one job a pull request cannot reach. Its own `concurrency` group `publish-allure-report` (no cancel) serialises publishes. Steps: checkout (with the default token, which `contents: write` makes able to push), `actions/download-artifact` of `allure-report` into `published-report/`, then the badge steps (next paragraph), then a step that switches to a fresh orphan `gh-pages` branch, copies the report in together with an empty `.nojekyll` and the `badges/` directory, commits as `github-actions[bot]` and runs `git push --force origin gh-pages`. The branch is rebuilt as one commit per publish so it does not accumulate report binaries; nothing is lost, because the previous runs' Allure history is inside the report as `history.jsonl` and the next `report` job reads it back from that branch. The final step appends `Allure report: https://n-orlov.github.io/s3-browser/` to `$GITHUB_STEP_SUMMARY`. The site is GitHub Pages serving the `gh-pages` branch root (enabling Pages is a repository setting, not part of the workflow). `src/__tests__/ciReporting.test.ts` fails if the step that runs `git push` loses its `github.event_name == 'push'` or `github.ref == 'refs/heads/master'` condition (also when the two are joined with `||`), if its job lacks `permissions: contents: write`, sits in `report`, stops needing `report`, or loses the summary link, and if any job a `pull_request` can reach (any job whose condition does not require a push event) has a permission other than read, whether its own or inherited from the workflow's `permissions`.
- **Badge publish (in `publish`).** Before the orphan rebuild, `publish` downloads the inputs of the badge renderer: artifacts `coverage-report` into `coverage/`, `unit-junit` into `junit/` and `eslint-result` (written by `quality`'s step `npx eslint . --format json --output-file reports/eslint.json || true`, run with `!cancelled()` after the gating Lint step, and uploaded from `reports/eslint.json`) into `reports/` (each `continue-on-error`, so a missing one only turns its badges `n/a`), and `e2e-test-results-*` into `e2e-results/<artifact>/` (a pattern download, which matches nothing without failing). It sets up Node 22.x and runs `npm audit --omit=dev --json > reports/audit.json` (failure tolerated), then `npm run --silent badges -- --out published-badges --e2e e2e-results/e2e-test-results-1/results.json --e2e e2e-results/e2e-test-results-2/results.json`, which writes the ten endpoint files. Every e2e shard's results file is named explicitly (never found by a loop over the files that exist, which would silently drop a missing shard), so a shard whose artifact did not arrive makes `e2e-tests` `n/a` instead of publishing the other shard's counts as the whole suite; an input that is absent renders `n/a` with colour `lightgrey`, never a stale or partial green badge. `src/__tests__/ciWorkflowPermissions.test.ts` fails when the badge step does not name every shard of the `e2e` matrix or selects results by existence. The `mutation` badge is produced by `mutation.yml`, not by this workflow, and the orphan rebuild would delete it, so a step runs `git fetch --depth=1 origin gh-pages` and `git show FETCH_HEAD:badges/mutation.json`, and when that file exists copies it over the freshly rendered `n/a` one (no previous commit or file leaves the `n/a` badge). The push step copies `published-badges/` to `badges/` beside the Allure report, so `https://n-orlov.github.io/s3-browser/badges/<name>.json` serves each badge. Badge steps run only in `publish`, which a pull request cannot reach. `src/__tests__/ciWorkflowPermissions.test.ts` fails when a step whose `run` mentions `badges` sits in a job reachable from `pull_request` (any workflow file), and when ci.yml's `publish` job has no step whose `run` invokes `npm run badges` or no step restoring `badges/mutation.json` from the previous `gh-pages` commit; negative fixtures cover a pull-request-reachable badge push and a ci.yml copy missing either step.
- **Job `gate`** (5-minute timeout, `needs: [quality, e2e, changes, release-dryrun]`, `if: always()`, `permissions: {}`): **the single status to protect** — branch protection should require `gate` and nothing else, so the matrix shard names and later job renames never have to be re-entered there. `if: always()` makes it run (and fail) when a need failed or was cancelled, and it also runs when a need was skipped, where a plain `needs` dependency would skip `gate` and a skipped required check reads as passing. It has one step that exports the four results into the environment. `quality`, `e2e` and `changes` must be exactly `success` (so `failure`, `cancelled` and `skipped` fail it; a `changes` that did not succeed fails it so that a broken path filter cannot read as "nothing to build"). `release-dryrun` must be `success` or `skipped`: it is skipped on an owner pull request that touches no packaging path, which passes, while `failure` and `cancelled` fail the gate. The `e2e` matrix is one need whose result is `success` only when both shards succeeded. It checks out nothing and runs nothing from the repository, so it uses a GitHub-hosted runner (`ubuntu-latest`) and a fork pull request cannot reach the self-hosted runners through it; `report` and `publish` are not part of it. `src/__tests__/ciReporting.test.ts` fails if `gate` loses either need, its `if: always()`, or the check of either result, and runs the step's script with `success`, `failure`, `cancelled` and `skipped` for each of `quality`, `e2e` and `changes` (only `success` passes); `src/__tests__/ciReleaseDryrun.test.ts` runs it with `release-dryrun` `skipped` (exit 0), `success` (exit 0), `failure` (exit 1) and `cancelled` (exit 1).
- **Job summaries.** The markdown is rendered by pure functions in `scripts/summary/jobSummary.ts` (no I/O; they also parse the report files' text); `scripts/summary/summary.ts` is the thin CLI that reads the files and appends to `$GITHUB_STEP_SUMMARY` (stdout when unset). `src/__tests__/jobSummary.test.ts` renders an all-green quality summary, a quality summary with a coverage total below its threshold, and an e2e shard with failed tests, and fails if the renderer drops any line those cases check.
- **Action pinning.** Every `uses:` in every file of `.github/workflows/` (today `ci.yml`, `release.yml`, `codeql.yml` and `mutation.yml`) references a full 40-hex commit SHA followed by a trailing `# <tag>` comment naming the release the SHA resolves to (for an annotated tag, the commit it peels to); Dependabot's `github-actions` entry moves the pins. `src/__tests__/ciActionPins.test.ts` builds its file list from a directory listing of `.github/workflows/` (no hard-coded array) and fails when a `uses:` ref in any of them is a tag, branch or short SHA.
- **CodeQL (`.github/workflows/codeql.yml`).** The `CodeQL` workflow runs static analysis for language `javascript-typescript` with the `security-extended` query suite (`build-mode: none`), on GitHub-hosted `ubuntu-latest` runners only. Triggers: `push` to `master`, `pull_request` targeting `master`, and a weekly `schedule` cron (Mondays 04:17 UTC). The workflow-level permission is `contents: read`; no job uses secrets. It has two jobs, because job permissions cannot be conditional. Job `analyze` has `if: github.event_name != 'pull_request'` (push and schedule), holds `security-events: write` at job level (the only place that permission appears in the file) and uploads the results to code scanning. Job `analyze-pr` runs only for a `pull_request` opened from this repository by `n-orlov` with actor `n-orlov` (the same owner gate as `ci.yml`), has `contents: read` only, and runs `analyze` with `upload: never`, so code reachable from a pull request never runs beside a write permission. The repository's CodeQL default setup stays not-configured, since an advanced workflow conflicts with it. `src/__tests__/codeqlWorkflow.test.ts` parses the file and fails if a trigger (push to master, pull_request, weekly schedule) is missing, if the language or query suite differs, if a runner is not `ubuntu-latest`, if the top-level permissions grant write, if `security-events: write` is on anything but the single job that uploads, if that job's `if:` does not exclude `pull_request`, or if the pull-request job loses `upload: never` or the owner gate.
- **Mutation (`.github/workflows/mutation.yml`).** The `Mutation` workflow has one job, `mutation` (90-minute timeout), on the self-hosted runners (`self-hosted, linux, x64, s3-browser`), with the same pull-request owner gate as `ci.yml` (same-repo head, author and actor `n-orlov`; `pull_request_target` is not used) and workflow permission `contents: read`. Triggers: a weekly `schedule` (cron `41 6 * * 1`, Mondays 06:41 UTC), `workflow_dispatch`, and `pull_request` targeting `master` or `main` filtered by `paths`, whose list is exactly the `mutate` list of `stryker.config.mjs` (the eight modules of section 4), so a pull request that touches no mutated module does not start it. Steps: checkout without persisted credentials, Node 22, `npm ci --no-audit --no-fund`, `npm run mutation` (the whole-run break plus the per-module check of section 4), a step with `if: always()` that re-judges the written report with `npm run --silent mutation -- --check-only` and appends the `MUTATION <score>  <module>` lines to `$GITHUB_STEP_SUMMARY` (so the per-module scores appear even when the run failed), and an `actions/upload-artifact` step with `if: always()` that uploads `reports/mutation/` (`mutation.html` and `mutation.json`) as artifact `mutation-report`, kept 14 days. A second job, `publish` (`needs: mutation`, 10-minute timeout, self-hosted), publishes the mutation badge: its `if:` is `!cancelled()` and the event is `schedule` or `workflow_dispatch` and `github.ref` is `refs/heads/master`, so a pull request (and a dispatch from another ref) never runs it. It holds `contents: write` at job level only (the workflow-level permission stays `contents: read`), and its `concurrency` group is `publish-allure-report` with `cancel-in-progress: false`, the group of `ci.yml`'s `publish`, so the two never push `gh-pages` at once. It downloads artifact `mutation-report` into `reports/mutation/` (`continue-on-error: true`: a mutation run that failed before writing `reports/mutation` uploads no artifact, and the missing download must not stop the job, so the later render and commit steps still run and publish `mutation` as `n/a` / `lightgrey` instead of leaving the previous run's green badge on `gh-pages`; a run that did write a report publishes its real score, which stays until the next mutation run), runs `npm run --silent badges -- --mutation reports/mutation/mutation.json` into a temp directory and keeps only its `mutation.json`, then fetches the existing `gh-pages` branch, switches to it and commits only `badges/mutation.json` on top (no orphan, no force, no other path added; nothing is committed when the file is unchanged) and pushes it. The Allure report and the other badges `ci.yml` published therefore survive, and `ci.yml`'s next `publish` carries `badges/mutation.json` over (Badge publish bullet). After a dispatch of the workflow on master, `https://n-orlov.github.io/s3-browser/badges/mutation.json` serves the shields endpoint JSON and the report's `index.html` still answers 200. No job of `ci.yml` `needs` it and `ci.yml` does not run it, so `gate` is independent of it. `src/__tests__/mutationWorkflow.test.ts` parses the file and fails if a trigger is missing, if `paths` differs from the parsed `mutate` list (its fixtures drop and add one path), if the publish job's `if:` admits `pull_request`, its permission is not job-level `contents: write` or another job holds a write, its concurrency group differs from `ci.yml`'s `publish`, it orphans, forces or adds more than `badges/mutation.json`, if the runner, the owner gate, the SHA pins (all jobs), the `if: always()` summary or upload step or the artifact name change, or if `ci.yml` references the workflow.
- **E2E soak (`.github/workflows/e2e-soak.yml`).** The `E2E soak` workflow runs the whole Playwright suite repeatedly to surface flaky tests. Triggers: a nightly `schedule` (cron `17 2 * * *`, 02:17 UTC, run on the default branch) and `workflow_dispatch` with the string input `repeat` (default `3`; a scheduled run has no inputs and falls back to `3`); there is no `pull_request` trigger, so nothing from a fork executes on the self-hosted runners. Its one job, `soak` (180-minute timeout, workflow permission `contents: read`), runs on the self-hosted runners (`self-hosted, linux, x64, s3-browser`) as a 2-way shard matrix (`shard: [1, 2]`, `fail-fast: false`). Steps: checkout without persisted credentials, Node 22, then `./scripts/e2e-docker.sh --repeat-each="$REPEAT" --shard=<i>/2` (it rejects a `repeat` that is not a positive integer, and `CI=true`), and three `actions/upload-artifact` steps, each with `if: always()` and kept 14 days: `playwright-report/` as `soak-playwright-report-<i>`, `test-results/` as `soak-test-results-<i>` and `allure-results/` as `soak-allure-results-<i>`. All actions are pinned to 40-hex SHAs. `playwright.config.ts` keeps `retries: 0`, so a test that fails in any one repeat fails the shard rather than passing on a rerun, plus `workers: 1`, `timeout: 60000` and `expect.timeout: 10000`. The `concurrency` group is exactly the expression `ci.yml` uses (`ci-${{ github.event.pull_request.number || github.ref }}`, which on the default branch is the group of a push to master), with `cancel-in-progress: false`, so a soak waits for a push CI (and the reverse) instead of running beside it or cancelling it. No job of `ci.yml` `needs` the soak and `ci.yml` does not reference it. `src/__tests__/e2eSoakWorkflow.test.ts` parses the file and fails if the nightly schedule, the dispatch input or its default, the `--repeat-each` wiring, the 2-shard matrix, an `if: always()` upload, the shared concurrency group, a SHA pin or the isolation from `ci.yml` is wrong, and if `playwright.config.ts` loses any of the four settings above (its fixtures remove the schedule and set `retries: 1`). The same test pins the timeout bounds: no `ci.yml` job (`quality` 20, `e2e` 40, `report` 15, `gate` 5, `publish` 10) may exceed the `timeout-minutes` it had before the soak existed and the soak job may not exceed 180, so a raised timeout fails (its fixtures raise `e2e` to 41, `quality` to 30, `report` to 16 and the soak to 181, and remove the soak's).
- **Dependency updates.** `.github/dependabot.yml` (version 2) has exactly two update entries, `npm` and `github-actions`, each at directory `/` with a `weekly` schedule and a group whose `update-types` are `minor` and `patch`, so minor and patch updates arrive as one grouped pull request per ecosystem and major updates arrive individually. The `npm` entry ignores `typescript` versions `7.x` (with a comment giving the reason): typescript-eslint 8.71.x peers `typescript <6.1.0` and the TypeScript 7 package exports no classic compiler API, so `typescript` stays on 6.0.x until typescript-eslint supports 7. `src/__tests__/dependabotConfig.test.ts` fails when an ecosystem, the weekly interval, the grouping or the typescript 7 ignore is missing.
- **Release.** Packaging and release run from `.github/workflows/release.yml` on GitHub-hosted runners, separately from this workflow. The Linux job runs `npm run sbom` after the tests and lists `sbom/sbom.cdx.json` in the `files:` of its release-attach step, so every release carries the production-dependency CycloneDX SBOM next to the AppImage.

- **Badges.** `npm run badges -- --out <dir>` (`scripts/badges/render.ts`; the pure renderer is `scripts/badges/badges.ts`, tested by `src/__tests__/badges.test.ts`) writes ten shields.io endpoint files into `<dir>`, each `{ "schemaVersion": 1, "label", "message", "color" }`: `coverage-lines`, `coverage-branches`, `coverage-functions`, `coverage-statements`, `crap`, `lint`, `unit-tests`, `e2e-tests`, `mutation` and `audit`. The inputs are the ones the job summary reads plus the mutation report and the audit: `coverage/coverage-summary.json`, `coverage/crap-summary.json`, `junit/junit.xml`, Playwright `test-results/results.json` (`--e2e <file>`, repeatable, summed over the shards; every named file must be present and parseable, so one absent or unreadable shard makes the whole `e2e-tests` badge `n/a` rather than a partial sum), `reports/mutation/mutation.json` (`--mutation`), `npm audit --omit=dev --json` output at `reports/audit.json` (`--audit`), ESLint's own result (`eslint --format json`) at `reports/eslint.json` (`--eslint`) and `.ratchet.json`, which supplies the coverage thresholds and `mutationScoreMin` (never the lint count: `maxWarnings` is a ceiling, not a measurement). Colour rules: a coverage badge is red below its `.ratchet.json` threshold, yellow from the threshold up to threshold + 5 points, and green (`brightgreen`) from threshold + 5; `mutation` follows the same rule against `mutationScoreMin`, using the whole-report score (Killed + Timeout over Killed + Timeout + Survived + NoCoverage). `crap` (functions over `CRAP_MAX`) is green only at 0 and red otherwise. `lint` shows the warning count from the ESLint result (`N warnings`, singular for 1), is green only at 0 warnings and 0 errors, yellow with warnings only, and red with any error (`E errors, N warnings`). `unit-tests` and `e2e-tests` are green with no failure and red on any failure. For `e2e-tests` a failure is a failed test (`stats.unexpected`) or any entry in the report's top-level `errors` array (a throwing `globalSetup`/`globalTeardown`, a crashed worker: all `stats` stay zero, Playwright exits 1), summed over the shards, so the badge reads `N report error(s), P passed` in red, alone or beside a passing shard, and never `0 passed` green; the e2e job summary marks such a shard ❌ with `, N report error(s)` after the skipped count. `audit` reports the high+ production findings (high plus critical, the same gate as `audit:prod`) as `N high+ vulnerabilities` (singular for 1): green at 0, red otherwise; low and moderate findings are not counted and never colour or fill the badge. A missing or unreadable input (for `lint`, an absent or malformed ESLint result) renders that badge as `message: "n/a"`, `color: lightgrey` and never fails the command; a missing `--out` exits `2`. `staticBadges(pkg)` in the same module derives the static license, Electron major and Node major badges from `package.json` (`license`, the major of `devDependencies.electron` and of `engines.node`), so they follow the file instead of being written by hand; `package.json` declares `engines.node` as `>=22`, the Node version CI runs the quality scripts on.
- **README badge row.** `npm run badges:readme` (`scripts/badges/readme.ts`; the pure generator is `scripts/badges/readmeBlock.ts`) rewrites only the block between the `<!-- badges:start ... -->` and `<!-- badges:end -->` comments at the top of `README.md`, and nothing outside them; running it twice leaves `git diff README.md` empty. The block holds: workflow status badges (`badge.svg?branch=master`, each linking to its workflow page) for `ci.yml`, `codeql.yml`, `mutation.yml` and `e2e-soak.yml`; a shields endpoint badge for each of the ten metric files at `https://n-orlov.github.io/s3-browser/badges/<name>.json` (`BADGE_NAMES`); the license, Electron and Node static badges from `staticBadges(package.json)`; and an Allure report link badge to the Pages root. `src/__tests__/readmeBadges.test.ts` fails when the committed block differs from the generator output (so changing the badge list, `package.json` license, `devDependencies.electron` or `engines.node` requires re-running the command and committing `README.md`), when a workflow badge names a file missing from `.github/workflows/`, or when a metric badge URL names a file the renderer does not emit.
