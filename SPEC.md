# S3 Browser — Specification

S3 Browser is a desktop Electron application for browsing and editing objects in Amazon S3 (and S3-compatible endpoints). This document describes the product as the code implements it. The tests in `src/__tests__/` and this file are the tracked evidence for its behaviour.

## 1. Process model

The application has three kinds of code, each built by its own script.

| Process | Source | Build output | Role |
| --- | --- | --- | --- |
| Main | `src/main/` (`index.ts`, `ipc/`, `services/`) | `dist/main/` (`tsc -p tsconfig.main.json`) | Owns the window, the AWS SDK clients, the file system and every IPC handler. |
| Preload | `src/preload/index.ts` | `dist/preload/` (`tsc -p tsconfig.preload.json`) | Runs in an isolated context before the page and exposes `window.electronAPI` through `contextBridge`. |
| Renderer | `src/renderer/` (React 19) | `dist/renderer/` (`vite build`) | The user interface. It has no Node.js access and reaches the main process only through `window.electronAPI`. |

- `src/main/index.ts` enforces a single application instance (`app.requestSingleInstanceLock`); a second launch focuses the existing window. On `app.whenReady` it registers `registerCredentialsIpc`, `registerS3Ipc` and `registerAppStateIpc`, then creates one `BrowserWindow` (1200x800, minimum 800x600, no application menu). In development (`NODE_ENV=development`) it loads `http://localhost:5173`; otherwise it loads `dist/renderer/index.html`.
- The preload script exposes `platform` plus three groups of functions, each of which is a thin wrapper around `ipcRenderer.invoke` on one channel from section 2: `appState` (persistence), `aws` (profiles) and `s3` (bucket and object operations). `electronAPI.getObjectMetadata` is an alias for `s3.getObjectMetadata` and invokes the same channel.
- All requests are renderer-initiated request/response calls (`ipcRenderer.invoke` / `ipcMain.handle`). The main process sends no unsolicited events to the renderer.
- The main process holds the selected AWS profile name in memory (set by `aws:set-profile`). Every `s3:*` handler that talks to S3 resolves credentials from that profile. When none is selected, each of them returns `{ success: false, error: 'No AWS profile selected. Please select a profile first.' }` (`s3:delete-prefix` adds `deletedCount: 0, failedCount: 1`), with two exceptions that carry no `error` field:
  - `s3:upload-files` returns `{ success: false, results: [] }`;
  - `s3:delete-files` returns `{ success: false, results: [], deletedCount: 0, failedCount: <number of keys> }`.

## 2. IPC surface

Every channel is registered with `ipcMain.handle` by one of `registerCredentialsIpc` (`src/main/ipc/credentials.ts`), `registerAppStateIpc` (`src/main/ipc/appState.ts`) or `registerS3Ipc` (`src/main/ipc/s3.ts`). The tables below list each channel in the first column in backticks; the unit test `src/__tests__/ipcSpecParity.test.ts` fails when this list differs from the set of registered channels, or when the preload script invokes a channel that is not registered. Arguments are the positional parameters after the implicit event.

Result shapes: `FileOperationResult` is `{ success: boolean; error?: string }`. `ObjectMetadata` is the object's content type, size, last-modified time, ETag, storage class, tags and custom metadata.

| `s3:create-folder` | `bucket: string`, `prefix: string` | `FileOperationResult`; creates a zero-byte folder marker object | `{ success: false, error }` |

**Argument validation.** Every handler checks its positional arguments with the helper in `src/main/ipc/validate.ts` before doing any work; the renderer is not trusted. Argument types are: a *bucket name* is a non-empty string of at most 255 characters without `/`; an *object key* is a non-empty string of at most 1024 UTF-8 bytes; a *key prefix* is a string of at most 1024 UTF-8 bytes that may be empty (`prefix` of `s3:delete-prefix` and `s3:create-folder` must be non-empty); a *non-empty string* is at most 4096 characters (profile names, operation ids, local file paths, URLs); `string[]` arguments (`keys`, `filePaths`) are arrays whose items are all object keys, respectively non-empty strings; `newName` is an object key; `content` and `keyOrPrefix` are strings that may be empty. No string may contain a NUL character. Extra arguments are ignored. An argument of the wrong type, a missing argument or a value outside these shapes makes the call resolve (it never rejects) to the *Invalid input* column and the handler body does not run: no S3 request, no filesystem access, no dialog and no shell call. Where the result type has the `{ success, error }` shape the invalid-input result is `{ success: false, error }` with `error` of the form `Invalid argument '<name>': expected <shape>`; otherwise it is the neutral value in the column. The unit test `src/__tests__/ipcValidation.test.ts` holds one row per channel and fails when a registered channel has none.

**Content-read size cap.** `s3:download-content` (text and gzip) and `s3:download-binary-content` (binary, parquet, image) send a HEAD request first and compare `ContentLength` with the cap, 50 MB (`50 * 1024 * 1024` bytes) by default, defined in `src/main/contentLimits.ts` and overridable with the positive-integer environment variable `S3_BROWSER_MAX_CONTENT_BYTES` (bytes). An object above the cap resolves to `{ success: false, error }` where `error` names the limit, and no `GetObject` request is made. The cap applies to the stored size, so a `.gz` object is measured compressed; gunzip output is bounded separately by the same cap (`decompressGzip` in `src/main/services/gzipUtils.ts` passes it as `maxOutputLength`), so a small gzip bomb resolves to `{ success: false, error }` (`Gzip decompression failed: Decompressed content exceeds the maximum size of 50 MB (52428800 bytes).`) instead of exhausting memory. The helper `tryDecompressGzip` falls back to raw text for non-gzip input but rethrows that cap error. A failing HEAD resolves to `{ success: false, error }` with the service message and no download follows.

## 3. Security model

The following is what the code implements; behaviour that is absent is stated as absent.

- **Window isolation.** The `BrowserWindow` is created with `contextIsolation: true`, `nodeIntegration: false` and `sandbox: true`. The renderer cannot `require` Node modules; its only bridge is the `electronAPI` object built in the preload script.
- **Content Security Policy.** `src/renderer/index.html` sets `default-src 'self'; script-src 'self' blob:; style-src 'self' 'unsafe-inline'; img-src 'self' blob:; worker-src blob:; font-src 'self';`. No directive allows a remote (`http:`/`https:`) origin; `src/__tests__/csp.test.ts` parses the policy and fails if one appears. The Monaco editor is bundled from the `monaco-editor` package in `node_modules`: `src/renderer/monacoSetup.ts` passes it to the `@monaco-editor/react` loader (`loader.config({ monaco })`, so no CDN loader path is in effect) and serves its web workers as inlined blob workers built from the same package.
- **Credentials.** AWS credentials are read in the main process from the standard AWS shared config and credentials files and never cross the IPC boundary in clear text. `aws:get-profile-details` masks the access key (first and last four characters), replaces the secret key and session token with `********` and the credential process with `(configured)`. `getCurrentProfileCredentials` is internal to the main process.
- **External links.** `src/main/windowSecurity.ts` (`secureWebContents`, called from `createWindow`) installs a `setWindowOpenHandler` that denies every new window. It passes the requested URL to `shell.openExternal` only when `isExternalOpenAllowed` (`src/main/externalUrlPolicy.ts`) accepts it: the scheme must be `https:` or `mailto:`. `http:`, `file:`, `javascript:`, `data:`, custom protocols and strings that do not parse as a URL are denied and never reach `shell.openExternal`.
- **Navigation.** `secureWebContents` handles `will-navigate` and `will-redirect` on the main window's `webContents` and calls `preventDefault` for any target outside the application origin (the Vite dev server origin in development; the exact `index.html` file URL in production, ignoring query and fragment). Same-origin navigation proceeds. A blocked navigation is not forwarded to the system browser.
- **IPC input.** Every `ipcMain.handle` handler validates the shape of its arguments at runtime through `src/main/ipc/validate.ts` before doing any work, in addition to typing them with TypeScript (section 2, *Argument validation*). A call with an invalid argument resolves to the invalid-input result and the handler body does not run.
- **Errors.** Invalid arguments never reach these paths: they resolve to the invalid-input result of section 2. Every `s3:*` handler whose result has a `success` field catches errors thrown by the AWS SDK or the file system and returns `{ success: false, error }` (for `s3:delete-prefix`, together with `deletedCount: 0, failedCount: 1`), except two that return no `error`: `s3:upload-files` reports per-file failures in `results[].error`, and an error escaping the loop yields `{ success: false, results: [] }`, dropping the results already collected; `s3:delete-files` reports per-key failures in `results[].error`, and an error escaping the loop yields `{ success: false, results: [], deletedCount: 0, failedCount: keys.length }`. `app-state:save` returns `{ success: false, error }` when the state file cannot be written. The `aws:*` handlers, `app-state:load`, `s3:cancel-operation`, `s3:get-parent-prefix`, `s3:get-key-name`, `s3:clear-client`, `s3:show-open-dialog`, `s3:open-downloads-folder` and `s3:show-file-in-folder` have no handler-level catch; an error that reaches them rejects the renderer's `invoke` promise.
- **Downloads.** `s3:download-file` writes into the downloads folder using the final path segment of the key as the file name.
- **Single instance.** A second application instance quits immediately.
- **Workflow permissions.** No workflow in `.github/workflows/` grants a `write` permission (or `write-all`) at workflow top level; a write scope is declared only in the `permissions:` of the job that needs it. A job that holds any write permission must be unreachable from `pull_request` and `pull_request_target`: either its workflow has neither trigger, or the job's `if:` evaluates false for those events (for example `github.event_name == 'push'` or `github.event_name != 'pull_request'`). `src/__tests__/ciWorkflowPermissions.test.ts` enforces this over a directory listing of `.github/workflows/`, so a new workflow file is covered without editing the test, and fails on a condition it cannot parse. Its fixtures prove the checks fire for a top-level `contents: write` and for a pull_request workflow whose write job has no event gate.
- **Packaged files.** electron-builder's `build.files` in `package.json` is `dist/**/*` minus negated patterns for test paths (`__tests__`, `*.test.*`), `e2e`, `coverage`, source maps (`*.map`) and credential-shaped files (`.env*`, `*.pem`, `*.key`, `credentials`, `.npmrc`), so none of them ship in the asar. `src/__tests__/packageConfig.test.ts` fails if any of those exclusions is missing (its fixtures: a `files` list without them, and one with the `*.map` exclusion dropped), and if the release workflow's upload globs do not match the configured targets (`AppImage` to `release/*.AppImage`, `nsis` and `portable` to `release/*.exe`; its fixture uploads `release/*.deb` instead).
- **Repository secret protection.** GitHub secret scanning and secret-scanning push protection are enabled on the `n-orlov/s3-browser` repository (`security_and_analysis.secret_scanning.status` and `security_and_analysis.secret_scanning_push_protection.status` both read `enabled` through the repository API), so a push containing a recognised provider secret is rejected and a committed one raises an alert. This is a repository setting, not code: nothing in the tree enforces it.

## 4. Quality gates

All gates run locally with the `package.json` scripts; CI runs the same commands.

| Script | Command | Gate |
| --- | --- | --- |

| `lint` | `eslint . --max-warnings 0` | ESLint at zero warnings: any warning fails the gate. |
| `test:coverage` | `vitest run --coverage` | Unit tests (jsdom) with V8 coverage; thresholds in `vitest.config.ts` are lines 92, functions 89, branches 83, statements 90 (each is the measured total, rounded down, minus 1). `src/main/index.ts` and `src/preload/index.ts` are excluded from coverage. The same run writes, next to the console output: Allure result files from `allure-vitest` into `allure-results-unit/`, a JUnit XML file at `junit/junit.xml`, and the coverage reports in `coverage/` (`coverage-final.json`, which `crap` reads, plus `coverage-summary.json` from the `json-summary` reporter, `lcov.info` and the HTML report). `vitest.config.ts` sets `coverage.reportOnFailure: true`, so a run with a failing test or a suite that fails to load still writes the coverage reports. `allure-results-unit/`, `junit/` and `coverage/` are git-ignored. |

| `test:e2e:docker` | `./scripts/e2e-docker.sh` | Runs the Playwright Electron suite in `e2e/` against LocalStack, entirely in containers: a LocalStack container plus a Playwright-image container that runs `npm ci`, `npm run build` and `xvfb-run npx playwright test`. **CRAP gate.** `npm run crap` scores every function in `src/main`, `src/preload`, `src/renderer` and `src/shared` (the directories that exist; tests and `.d.ts` files are skipped) as `CRAP = c^2 * (1 - cov)^3 + c`, where `c` is the function's cyclomatic complexity from ESLint's `complexity` rule and `cov` is the fraction of the function's own statements (nested functions excluded) that ran, read from `coverage/coverage-final.json`. A function in a file that has no coverage entry has `cov = 0`. Scoring is `scripts/crap/crapScore.ts`; the CLI is `scripts/crap/crap.ts`. The command prints each offending function as `CRAP <score>  <file>:<qualified name>` and exits non-zero when any function fails; it exits `2` when `coverage/coverage-final.json` is missing, so run `npm run test:coverage` first. A function id is `<file>:<qualified name>` (repeated names in a file get `#2`, `#3`, ... in source order).

- **Limit.** A function not in the baseline fails when its score exceeds `CRAP_MAX` (environment variable, default `20`, the `DEFAULT_CRAP_MAX` constant of `scripts/crap/crapScore.ts`). The limit only goes down: `.ratchet.json` records it as `crapMax` (`20`).
- **Baseline.** `crap-baseline.json` maps function ids to the score they had when the baseline was last written. It lists exactly the functions over `CRAP_MAX` at that time; it is now `{}` (every function scores at most `CRAP_MAX`), and `ratchet:check` keeps it that way (see the ratchet gate). `npm run crap -- --write-baseline` regenerates it from the current code and coverage (honouring `CRAP_MAX`); it is the only supported way to edit it.
- **Shrink-only.** The baseline is `{}` and `ratchet:check` keeps its size at `crapBaselineMax` `0`, so the baseline never grows and no function over the limit can be listed; the two functions that scored 30 when the limit was lowered (`App.handleCopyUrl`, `FileList.handleScroll`) are covered by unit tests instead. A baselined function fails when its score exceeds its baseline entry, even if the score is below `CRAP_MAX`, so the baseline can only improve: lowering an entry by hand below the live score makes the gate fail, and a function that gets better is locked in by regenerating the baseline. Entries for functions that no longer exist are ignored and reported.

**Ratchet gate.** `.ratchet.json` records the quality ceiling and floors: `maxWarnings` (the lint warning ceiling), `crapBaselineMax` (the allowed number of entries in `crap-baseline.json`), `crapMax` (the CRAP limit ceiling, `20`) and `coverageThresholds` (`lines`, `functions`, `branches`, `statements`) and `mutationScoreMin` (the mutation break floor, `80`). `maxWarnings` and `crapBaselineMax` are both `0`. `npm run ratchet:check` reads the `--max-warnings` value from the `lint` script in `package.json`, the number of entries in `crap-baseline.json`, `DEFAULT_CRAP_MAX` from `scripts/crap/crapScore.ts`, the four `coverage.thresholds` from `vitest.config.ts` and `thresholds.break` from `stryker.config.mjs`, prints one `RATCHET` line per regression and exits `1` when `.ratchet.json` records any `maxWarnings` or `crapBaselineMax` other than `0`, when `--max-warnings` is higher than `maxWarnings`, when `crap-baseline.json` has more entries than `crapBaselineMax` (so a function over `CRAP_MAX` can no longer be baselined), when `DEFAULT_CRAP_MAX` is higher than the recorded `crapMax` or `.ratchet.json` records a `crapMax` above `20`, when any threshold is lower than its recorded value, when the Stryker `thresholds.break` is lower than `mutationScoreMin`, or when `.ratchet.json` records a `mutationScoreMin` below `80`; it exits `2` when an input is missing or unreadable (a `.ratchet.json` without a numeric `crapMax` or `mutationScoreMin` included), and `0` otherwise. `src/__tests__/strykerConfig.test.ts` additionally fails when `thresholds.break` differs from `mutationScoreMin` or when the config's `mutate` list differs from the closed set its header comment names. The same command also compares the working tree with the merge base: it reads the four coverage thresholds, the lint `--max-warnings`, `DEFAULT_CRAP_MAX`, the `crap-baseline.json` entry count and the Stryker `thresholds.break` from `vitest.config.ts`, `package.json`, `scripts/crap/crapScore.ts`, `crap-baseline.json` and `stryker.config.mjs` as they stand at `git merge-base HEAD origin/master` (`git show`), prints one `RATCHET` line naming each value that is looser than at the base (a lower threshold or break, a higher `--max-warnings` or CRAP limit, a larger baseline) and exits `1`, so lowering a threshold in `vitest.config.ts` and `.ratchet.json` together no longer passes. A value the base does not have (a missing file, or a field its reader cannot find) is unconstrained, and a tighter value passes. It exits `2` when there is no merge base (no `origin/master` ref, or no common ancestor), so a CI checkout fetches `origin/master` before running it. A coverage threshold or mutation break that is stricter than the record passes and the command prints which `.ratchet.json` entries to tighten; the lint ceiling and the baseline size have no looser or stricter state, so a non-zero `maxWarnings` or `crapBaselineMax` is a violation even when the `lint` script agrees with it. Logic is `scripts/ratchet/ratchetCheck.ts`; the CLI is `scripts/ratchet/ratchet.ts` and runs from the repository root.

**Mutation gate.** `npm run mutation` runs Stryker (`@stryker-mutator/core` with `@stryker-mutator/vitest-runner`, both devDependencies; config in `stryker.config.mjs`) over a closed set of 8 modules: `scripts/crap/crapScore.ts`, `scripts/ratchet/ratchetCheck.ts`, `scripts/summary/jobSummary.ts`, `src/main/ipc/validate.ts`, `src/main/externalUrlPolicy.ts`, `src/main/windowSecurity.ts`, `src/main/services/s3Url.ts` and `src/main/services/gzipUtils.ts` (the `mutate` list is exactly these files and the config's header comment names them). Stryker's `thresholds.break` is `80`, but it judges only the whole run, so `scripts/mutation/mutation.ts` then scores every module of the set on its own from `reports/mutation/mutation.json` and exits `1` when any module scores below the break (score = (Killed + Timeout) / (Killed + Timeout + Survived + NoCoverage); a module missing from the report or without a scoreable mutant also fails), printing one `MUTATION <score>  <module>` line per module and `MUTATION FAIL <module>: ...` per failure; it exits `2` when the report is unreadable. `npm run mutation -- --check-only [report]` skips Stryker and judges an existing report. The pure scoring is `scripts/mutation/mutationCheck.ts`, tested by `src/__tests__/mutationCheck.test.ts`. The HTML (`mutation.html`) and JSON (`mutation.json`) reports are written to the git-ignored `reports/mutation/`; Stryker's sandbox is `.stryker-tmp/` (also git-ignored). A module task runs `npx stryker run --mutate <file>` on its own file only.

The mutation set also runs in CI as the weekly `Mutation` stage of the `Jenkinsfile` (section 5); it is not part of the `jenkins/gate` status of an ordinary build.

Two repository files adapt Stryker to Vitest 5. `vitest.mutation.config.ts` is `vitest.config.ts` minus the allure setup file and reporters (Stryker's sandbox symlinks `node_modules`, and `allure-vitest/setup` does not resolve from there); the tests and assertions are the same. `scripts/mutation/vitestFileRunner.mjs` registers the test runner `vitest-file`: `@stryker-mutator/vitest-runner` 10 narrows a mutant run with a test-name regex built from space-joined names, which Vitest 5 (it matches `describe > test`) never matches, so every mutant would survive with zero tests run; the wrapper narrows each mutant run to the covering test files instead and otherwise delegates to the vitest runner.

**No fixed sleeps in e2e.** `eslint.config.mjs` applies `no-restricted-syntax` at severity `error` to `e2e/**` with selectors matching every call of `waitForTimeout` (member or bracket form), so `npm run lint` fails on a fixed sleep; tests wait on web-first assertions or `expect.poll` instead, and the rule is never silenced with `eslint-disable`. `src/__tests__/e2eNoFixedSleep.test.ts` lints fixtures through the ESLint Node API and fails if the rule is removed.

`playwright.config.ts` runs one worker, sequentially, with `retries: 0` everywhere (a flaky test fails the run), and forbids `test.only` in CI.

**Flaky detection (retries stay 0).** Neither runner retries: `retries: 0` in `playwright.config.ts` and no `retry` in `vitest.config.ts`, so a test that fails once fails its run. Both configs also write a JSON report to a fixed path: `vitest.config.ts` adds the `json` reporter writing `junit/vitest-results.json` (next to `junit/junit.xml`), `playwright.config.ts` writes `test-results/results.json`. Flakiness is detected across whole repeated runs instead: `node ci/mark-flaky.mjs --junit <junit.xml> [--junit <junit.xml> ...] --count-file <file> <report.json> [...]` (every `--junit` file is rewritten, one per shard of a sharded suite) reads JSON reports of one suite (vitest or Playwright shape) that add up to two or more runs, and compares each test's outcome per run; a vitest report is one run, and a Playwright report written with `--repeat-each=N` counts as N runs (entry k of a spec's `tests` is repeat k), so an unsharded soak needs one report; a sharded one needs all shards' reports in one call. A test that failed in at least one run and passed in at least one other becomes one passing `<testcase>` in the JUnit XML, which is rewritten in place: its `<failure>`/`<error>` children turn into `<rerunFailure>` children (one per failed run) and the `failures`/`errors` counters of its `<testsuite>` and `<testsuites>` drop accordingly. A test that passed in every run is left alone; a test that failed in every run stays failed and is not counted. The number of marked tests is written to `--count-file`. The script exits `2` with fewer than two runs in total or an unreadable input. `src/__tests__/flakyMarker.test.ts` fails when either config has a non-zero `retries`/`retry` or no `json` reporter with a fixed `outputFile` (checked against a fixture config with `retries: 1`), and runs the script over three named fixtures: a fail-then-pass test (marked, count 1), a pass-pass test (unmarked) and a fail-fail test (stays failed, not counted); it is red when the script is replaced by a no-op.

## 5. CI topology

**Jenkins CI lane (`Jenkinsfile`).** The homelab Jenkins multibranch job `s3-browser/ci` builds every branch and every same-repository pull request (as `PR-<n>`, merged with the target) from the `Jenkinsfile` at the repository root; fork pull requests are never discovered. It is a declarative pipeline that loads the shared library with `@Library('homelab') _` and has `agent none`, so each stage names its own agent and a build never holds a phone while another stage runs elsewhere. Pipeline options: `ansiColor('xterm')`, `timestamps()`, `buildDiscarder(logRotator(numToKeepStr: '30'))`, `disableConcurrentBuilds()`, a 200-minute `timeout` ceiling (stages carry their own) and `copyArtifactPermission('/s3-browser/release,/s3-browser/ci/*')`, which lets the release job and this job's own next build copy artifacts. The agents' workspaces persist between builds, so a stage starts with `git clean -ffdxq`. `src/__tests__/repocheckCiLane.test.ts` asserts the six options, the Quality label, the memory cap and the order of the ten Quality steps, and is red for fixture Jenkinsfiles without `disableConcurrentBuilds`, without `--memory`, and with lint moved after build.

- **Stage `Quality`** (30-minute stage timeout, agent label `arm64 && docker && s3-browser`, the phones delta, hotel and bravo). The phones run musl, so every Node command runs through the `nodeSh` helper in a throwaway glibc `node:22` container with `--memory 3g --memory-swap 3g`, the workspace mounted at `/app`, the container run as the agent's uid, `CI=1`, and the npm cache kept on the agent (`$S3B_NPM_CACHE`, default `~/.cache/s3b-npm`); the container is named after the build tag so a killed stage can be cleaned up by name. After the reset it fetches `origin/master` into `refs/remotes/origin/master` (the base `ratchet:check` compares against; a PR merge checkout may not carry that ref), then runs, in this order and failing fast: `npm ci --no-audit --no-fund`, `npm run typecheck`, `npm run lint:report || true` (the ESLint JSON report for the build's reports, see below), `npm run lint`, `npm run test:coverage`, `npm run crap`, `npm run ratchet:check`, `npm run audit:prod`, `ci/trivy.sh` (on the agent, since the script drives the docker daemon itself), `npm run build` and `npm run sbom`.

- **Stage `E2E`** (after `Quality`; three parallel child stages `E2E shard 1/3`, `E2E shard 2/3` and `E2E shard 3/3`, each with a 20-minute stage timeout; the pipeline agent is none, so each shard takes its phone itself). Each shard calls the `e2eShard(<i>)` helper, which names the stage for the gate and asks for `node("arm64 && docker && s3-browser")` (the phones delta, hotel and bravo). On the node the shard body runs inside `lock(resource: "s3b-e2e-${env.NODE_NAME}", skipIfLocked: true)`: it checks out, resets with `git clean -ffdxq` and runs `CI=1 scripts/e2e-docker.sh --shard=<i>/3`. A shard shows 3 GB for Playwright plus 1 GB for LocalStack and delta has 7.5 GB with two executors, so the lock admits one shard per agent at a time; a shard whose node is locked does not wait for it (that would hold an executor and serialise two shards on one phone) but gives the executor back and asks again for a node other than the ones it was refused on (`... && !delta`), so the three shards end on three distinct phones. `scripts/e2e-docker.sh` runs on the agent itself and reads the Playwright version from `package-lock.json` with awk, because the phones have no host Node. Each shard has `post { aborted }` and `post { cleanup }` blocks that call `e2eShardCleanup(<i>)`: on the node the shard ran on (kept in `E2E_NODE_<i>`) it removes the shard's `s3b-` containers (selected by the `BUILD_TAG`-derived run id and the `-shard<i>-` infix of their names) with `docker rm -fv`, then the named volumes those containers mounted and the shard's `s3b-e2e-` network, so an aborted build or a script killed before its own trap ran leaves nothing behind. `src/__tests__/repocheckCiLane.test.ts` asserts the shard count of 3, the label, the lock around the script and the removal in both post blocks, and is red for fixture Jenkinsfiles without the lock, without the post blocks, with two shards and with a different label.
- **Stage `Release dry-run`** (after `E2E`; 20-minute stage timeout; `agent { label 'amd64 && docker && s3-browser' }`, i.e. int21h-ws, because the phones are arm64 and `scripts/smoke-appimage.sh` cannot run an x64 AppImage there). It runs when `branch 'master'` (always) or when the change touches a packaging path: `when { beforeAgent true; anyOf { branch 'master'; expression { env.PACKAGING_CHANGED == 'true' } } }`, so a skipped stage takes no executor. `PACKAGING_CHANGED` is set in `Quality` by `packagingChanged()`, which matches `git diff --name-only origin/master...HEAD` against `releasePaths()` with POSIX `case` patterns (the phones have no bash; `*` also matches `/`). The list is the packaging inputs plus the release definition files: `package.json`, `build/**`, `electron-builder*`, `Jenkinsfile.release`, `ci/release-build.sh`, `ci/release-stage.sh`, `vite.config.*` and `tsconfig*.json`. The stage resets with `git clean -ffdxq`, runs `npm ci` and `npm run build` through `nodeSh`, then `npx electron-builder --linux AppImage --x64 -p never` in the same memory-capped `node:22` container (`--x64` is explicit so the result does not depend on the agent's architecture; nothing is published; the Electron and electron-builder downloads are cached in the agent's npm cache directory), then `S3B_SMOKE_DOCKER_ARGS="--memory 3g" scripts/smoke-appimage.sh`. `scripts/smoke-appimage.sh` reads the Playwright version from `package-lock.json` with awk, so it needs no host Node. A failing stage names itself in the `jenkins/gate` failure description. `src/__tests__/repocheckCiLane.test.ts` asserts the label, `--x64`, the smoke call after the build, the `branch 'master'` condition, the `PACKAGING_CHANGED` condition and the path list, and is red for fixtures without `--x64`, without the master condition, without the smoke call, with an arm64 label and with `package.json` missing from the list.

- **Nightly lane (triggers).** The pipeline declares a boolean parameter `EXTENDED` (default `false`) and `triggers { cron(env.BRANCH_NAME == 'master' ? '17 2 * * *' : '') }`: a nightly build at 02:17 on `master` only, an empty spec (no trigger) on every other branch and pull request. `isNightly()` is the one question the lane's stages and the Telegram sound ask: the build has a `TimerTrigger$TimerTriggerCause`, or `params.EXTENDED == true`. Ticking `EXTENDED` by hand runs the lane on any branch or pull-request build (the parameter exists once a build of the `Jenkinsfile` has run, so the first build of a branch cannot be started with it). Every nightly stage runs on arm64 phones only (`arm64 && docker && s3-browser`), after `Release dry-run`, in the order `Soak`, `Stability`, `Trivy fresh DB`, `Mutation`; each is guarded by `isNightly()` in its `when` (`beforeAgent true` where the stage has its own agent), so a pull-request or `master` push build skips all four. `src/__tests__/repocheckNightly.test.ts` asserts the master-only cron, the `EXTENDED` parameter and the guard on each of the four stages, with red fixtures for a cron on every or on the non-master branches, no cron, no parameter and each guard removed.
- **Stage `Soak`** (three parallel child stages `Soak shard <i>/3`, each with a 60-minute timeout; the soak helper `soakShard(i)` takes `node("arm64 && docker && s3-browser${exclude}")`). The e2e suite with every test repeated three times: `CI=1 scripts/e2e-docker.sh --repeat-each=3 --shard=<i>/3` , inside the same per-node `lock(resource: "s3b-e2e-${env.NODE_NAME}", skipIfLocked: true)` and node-refusal loop as the `E2E` stage, so the three shards sit on distinct phones, one at a time per phone. `playwright.config.ts` keeps `retries: 0`: a test that fails in any one repeat fails its shard. In a `finally`, whatever the outcome, the shard stashes `junit/**` and `test-results/results.json` as `soak-results-<i>`. `--shard` spreads the repeats of one test over the shards, so no single shard's report shows a test failing in one repeat and passing in another: the pipeline's `post { always }` unstashes the three shards as `soak-<i>/` and runs `ci/mark-flaky.mjs` once over their three JSON reports, rewriting the three `junit/e2e-junit.xml` files (a fail-then-pass test gets `<rerunFailure>`) and writing `reports/flaky-count-soak.txt`. The stage's `post` removes the shard's containers and volumes with `e2eShardCleanup(<i>)`, as `E2E` does.
- **Stage `Stability`** (45-minute timeout; `agent { label 'arm64 && docker && s3-browser' }`). Three unit-suite runs, each from a clean state: `git clean -ffdxq` (keeping only `stability-out/`), `npm ci`, `npx vitest run` in the memory-capped `node:22` container (`nodeSh`). A failing run does not stop the others: each run's `junit/vitest-results.json` and `junit/junit.xml` are copied to `stability-out/run-<n>.json` and `junit-<n>.xml`. Then `ci/mark-flaky.mjs` runs over the three JSON reports, marking a fail-then-pass test in the last run's JUnit (`reports/stability-junit.xml`) and writing `reports/flaky-count-stability.txt`; only then does the stage `error` if any run failed, so a flaky test turns the nightly build red and is named in the report rather than hidden. The results are stashed as `stability-results` in the stage's `post { always }`.
- **Stage `Trivy fresh DB`** (20-minute timeout; `agent { label 'arm64 && docker && s3-browser' }`). `TRIVY_REPORT=reports/trivy-fresh.txt ci/trivy.sh --fresh`: the blocking Trivy gate of `Quality` (vuln, secret and misconfig, `HIGH,CRITICAL`, development dependencies included), but with the agent's cached vulnerability DB dropped first so the scan downloads a new one. The report is stashed as `trivy-fresh-results` and archived.
- **Nightly reports.** The pipeline's `post { always }` unstashes `stability-results`, `trivy-fresh-results` and `soak-results-<i>` (a stash of a stage that did not run is skipped), adds the counts of `reports/flaky-count-stability.txt` and `reports/flaky-count-soak.txt` into `reports/flaky-count.txt` (written only when at least one marker ran, so a build without them still reads `not measured`), which the CI summary page and the Telegram message show, and archives the Stability JSON and JUnit, the soak JUnit, `reports/trivy-fresh.txt` and the combined count.
- **Stage `Mutation`** (after `Release dry-run`; 90-minute stage timeout; `agent { label 'arm64 && docker && s3-browser' }`). The weekly Stryker run of section 4 over the eight-module set of `stryker.config.mjs`. Its `when` decides `beforeAgent true` and is `allOf` two conditions: the build is in the nightly lane (`isNightly()`, i.e. started by the cron trigger or with the `EXTENDED` parameter ticked), and it is Monday (`env.BUILD_DAY == '1'`, the ISO weekday in UTC that `Quality` records with `date -u +%u`) or `params.EXTENDED == true`; so the nightly lane mutates weekly on Mondays, an `EXTENDED` build always, and a pull-request or `master` push build never. It calls `gateStage('Mutation')`, resets the workspace, installs, and runs `npm run mutation` through `nodeSh`, i.e. in the throwaway `node:22` container with `--memory 3g --memory-swap 3g`; the script fails the stage when the whole-run score or any module's score is under `thresholds.break` (80). The stage's own `post { always }` publishes `reports/mutation` as the HTML report `Mutation` (`publishHTML`, file `mutation.html`, kept for every build) and stashes `reports/mutation/**` as `mutation-results`, red or green. The pipeline's `post { always }` unstashes it into the workspace, and `npm run badges:ci` computes the `mutation` badge (score with the colour against the ratchet's `mutationScoreMin`, `not run` when the stage did not run) which `setStatus`/`setColor` apply. `src/__tests__/repocheckNightly.test.ts` asserts the nightly guard, the Monday/`EXTENDED` guard, the HTML publish and the badge update, each with a red fixture. The GitHub `Mutation` workflow below stays until the workflows are retired.

- **Reports (pipeline-level `post { always }`).** The reports are built on every outcome, so a red build still shows what ran. The pipeline agent is none, so what the stages produced travels as stashes: `Quality` stashes `junit/`, `coverage/`, `allure-results-unit/`, `reports/` and `sbom/` in its own `post { always }` under `quality-results`, and each e2e shard stashes `junit/`, `allure-results/`, `playwright-report/` and `test-results/results.json` in a `finally` as `e2e-results-<i>` (a stash a stage never reached is skipped with a message). `post { always }` then takes an `arm64 && docker && s3-browser` node, checks out, and unstashes into the workspace (Quality's at the root, shard `<i>`'s under `e2e-<i>/`). It runs `junit` on `junit/junit.xml` (Vitest) and `e2e-*/junit/e2e-junit.xml` (the Playwright `junit` reporter, one file per shard) with `skipMarkingBuildUnstable: true` and `allowEmptyResults: true` (a failing test already fails its stage). It builds one Allure 3 report from `allure-results-unit` and each shard's `allure-results` (`npx allure@3.20.1 generate ... --config scripts/allurerc.mjs`, in the memory-capped `node:22` container): the history of the previous build comes from `copyArtifacts` (`projectName: env.JOB_NAME`, `lastCompleted()`, filter `allure-history/**`, `optional: true`), `previous/allure-history/history.jsonl` is copied to `allure-report/history.jsonl` before generation, and the new `history.jsonl` is copied to `allure-history/` and archived for the next build. `publishHTML` publishes `allure-report/` as the build-page report `Allure` (`keepAll`, `alwaysLinkToLastBuild`), and `archiveArtifacts` keeps `coverage/**`, `reports/eslint.json` (written by `npm run lint:report`, which `Quality` runs before `npm run lint`, so a red lint still leaves it), `sbom/**`, `reports/trivy.txt` (the scan output `ci/trivy.sh` also writes to `TRIVY_REPORT`, default `reports/trivy.txt`, red scan included), `e2e-*/playwright-report/**` and `allure-history/**`. **CI summary page.** After the Allure report, `post { always }` runs `node scripts/summary/summary.ts html ci-summary` (in the `node:22` container, inside a `catchError`) and `publishHTML` publishes `ci-summary/` as the build-page report `CI summary` (`keepAll`, `alwaysLinkToLastBuild`). The page is rendered by the pure `renderSummaryPage` in `scripts/summary/summaryPage.ts`, which reuses the report types and helpers of `scripts/summary/jobSummary.ts`, so it judges the numbers exactly as the GitHub job summaries do: the unit-test totals (`junit/junit.xml`), one row per e2e shard (`e2e-<i>/test-results/results.json`; a failed test or a report-level error marks the shard ❌), the four coverage totals each against its threshold from `vitest.config.ts` (a total below it reads `❌ miss`), the count of functions over `CRAP_MAX` (`coverage/crap-summary.json`) and the flaky-test count read from `reports/flaky-count.txt` (the file `ci/mark-flaky.mjs --count-file` writes; no file reads `not measured`, never 0). A report that was not produced renders as `no data`, never as zeros, and every printed value is HTML-escaped. `src/__tests__/jobSummary.test.ts` renders the page from fixture reports with flaky count 2 and asserts the counts and the `2 flaky tests` line (it is red when the HTML writer writes nothing), and `src/__tests__/repocheckCiLane.test.ts` fails if `post { always }` stops rendering or publishing the page. None of these steps posts the gate; `jenkins/gate` stays with `post { success }` and `post { unsuccessful }`.
- **Jenkins README badges (in `post { always }`).** The `Jenkinsfile` configures embeddable build status badges with `addEmbeddableBadgeConfiguration`: `tests`, `coverage`, `quality` and `mutation`, besides the plugin's built-in `build`. All four are declared on every build with status `not run` and colour `lightgrey`, so a build that produced no report shows `not run` and never the previous build's numbers. After the CI summary page, `npm run badges:ci -- ci-summary/badges.txt` (`scripts/badges/jenkins.ts`; the pure derivation is `scripts/badges/jenkinsBadges.ts`, tested by `src/__tests__/jenkinsBadges.test.ts`) reads `junit/junit.xml`, every `e2e-<i>/test-results/results.json`, `coverage/coverage-summary.json`, `coverage/crap-summary.json`, `reports/eslint.json`, `reports/mutation/mutation.json` and `.ratchet.json` and writes one `<id>=<status>|<color>` line per badge; the `Jenkinsfile` splits each line and calls `setStatus` and `setColor` on the matching badge (inside `catchError`, so a failed render leaves `not run`). `tests` is `<n> passed` in `brightgreen` (unit plus e2e passed tests) and `<n> failed` in `red` on any failed test or e2e report error; `coverage` is the line coverage against the `.ratchet.json` floor (red below it, `yellow` within 5 points, `brightgreen` from 5 points above); `quality` is `passing` in `brightgreen` only with no CRAP offender and no ESLint warning or error, `failing` in `red` otherwise; `mutation` is the whole-report mutation score with the same colour rule against `mutationScoreMin` (`not run` while no `reports/mutation/mutation.json` exists, i.e. on every build that does not run Stryker). The Jenkins `embeddable-build-status` plugin serves the SVGs publicly at `https://int21h.mooo.com/jenkins-static/s3-browser/ci/<branch>/<id>.svg`; the README uses the `master` branch. `src/__tests__/repocheckCiLane.test.ts` fails when `post { always }` lacks the configuration of any of the four badges or never sets their status and colour (fixtures drop the mutation badge and the `setStatus`/`setColor` calls).

- **Telegram notification (pipeline-level `post { cleanup }`).** Every build posts one Telegram message through `notifyTelegram` (`notifyOn: 'ALL'`) from the shared library. It is the last step of `post { cleanup }`, which runs after `always`, `success` and `unsuccessful`, so the message carries the final result; it reads `Result: <result> · flaky tests: <n>` (the count `post { always }` reads from `reports/flaky-count.txt` into `env.FLAKY_COUNT`, `not measured` when no flaky pass ran) plus ` · nightly (extended lane)` on a nightly build; the library adds the failed stage, the commit and the test counts. A sound is requested only when the build is `FAILURE` or `ABORTED` and its branch is `master` or it is a nightly build (`isNightly()`: a cron-started build, or one with `EXTENDED` ticked): `silent: !sound`, so every other message (pull requests, green builds, `UNSTABLE`) arrives silently. Delivery is best-effort: the call and its node request sit in a `try`/`catch` whose `catch` only logs, so a Telegram outage or a missing agent never changes the build result, and the message is never a success condition. `src/__tests__/repocheckCiLane.test.ts` asserts the call sits in `post { cleanup }` as its last step, the try/catch, the result and flaky count in the text and the sound condition, and is red for fixtures with the call moved to `post { always }`, with a step after it (outside and inside the node block), with sound on any red build, with sound on `UNSTABLE`, without the try/catch and without the flaky count.

- **Gate status `jenkins/gate`.** The `Jenkinsfile` posts the commit status context `jenkins/gate` itself, through the GitHub statuses API (`POST /repos/n-orlov/s3-browser/statuses/<sha>`), from the `postGate` helper, inside `withCredentials` on the Jenkins credential `github-n-orlov` (the token is read nowhere else). The sha is the revision Jenkins selected for the build, resolved by `ci/gate-sha.sh` (`gateSha`): for a branch build (no `CHANGE_ID`) it is `HEAD`; for a pull request build it is the pull request head Jenkins pinned when it scheduled the build. Jenkins' checkout runs `git checkout -f <pinned head>`, then, with the merge strategy, `git merge <pinned target>`, then `git checkout -f <result>`, so `HEAD` is either the pinned head itself (a simple commit, or any merge commit the pull request carries, when the target merge was a no-op) or a commit the target merge produced from it (a synthetic merge, or the target tip after a fast-forward). Neither the fetched ref `refs/remotes/origin/PR-<CHANGE_ID>` (it names whatever the head was at fetch time, which is newer than the pinned head when the pull request is pushed again between scheduling and checkout) nor the commit's parents, subject or presence on a remote ref is evidence: a pull request head can be a merge commit made on a detached `HEAD` (subject `Merge ... into HEAD`, the same as Jenkins' merge) that was force-pushed away before the checkout's fetch. The evidence is the checkout's own `HEAD` reflog: walking it newest first and skipping entries that did not move `HEAD` (the final re-checkout), when the first entry that moved `HEAD` is a `merge ...` entry ending at `HEAD` the script prints the commit that merge started from (the pinned head), and when it is any other entry ending at `HEAD` (the `checkout: moving from ... to <pinned head>` entry) it prints `HEAD`. So an actual pull request merge head is never replaced by its first parent, a synthetic merge on top of any head resolves to that head, and a fast-forward of the target over the head resolves to the head rather than the target tip. When the workspace has no `HEAD` reflog, or the reflog does not record how `HEAD` got where it is, the script exits non-zero instead of posting a status on a guessed sha. `src/__tests__/gateSha.test.ts` builds a bare origin publishing `refs/pull/<id>/head`, a developer clone and a workspace that replays Jenkins' fetch, pinned checkout, merge and re-checkout, for each case: simple head, synthetic merge, merge-commit head with and without a synthetic merge, a detached-`HEAD` merge head force-pushed away before the fetch (no-op target merge), a detached-`HEAD` merge head under a synthetic merge, a head whose subject is exactly Jenkins' `Merge commit '<sha>' into HEAD`, a target merge that fast-forwards over the head, a reused workspace whose previous build left a synthetic merge, the pull request moved on after the pin (direct checkout, synthetic merge, and a merge-commit pin), the target moved after the pin, a merge of the target by name, a merge-commit head no remote ref contains, a workspace without a reflog, and a branch build. It is red against the first-parent-of-any-merge rule, against the earlier rule that trusted the fetched ref and against the rule that recognised the synthetic merge by its subject and remote refs. The state is `pending` (description `Build running`) when the `Quality` stage starts, `success` only from `post { success }`, and `failure` from `post { unsuccessful }`, which covers FAILURE, ABORTED and UNSTABLE builds, with a description of the form `Build <result> in stage <name>` naming the stage recorded by `gateStage` (`startup` when no stage had started). `target_url` is the build URL. - **Working practice (Jenkins).** This is the rule changes follow to reach `master`; CLAUDE.md's *Working practice* states the same. One branch per scope of work, cut from `master`. The pull request stays a draft until the scope is complete. Jenkins builds a draft pull request like any other same-repository pull request and posts `jenkins/gate` on it (the live `s3-browser/ci` job discovers origin pull requests with no draft exclusion), so a draft's check is real; the draft state only says the scope is not done. The required check is the commit status `jenkins/gate`, green on the pull request head. The pull request is squash merged, so a push to `master` is the squash merge of a pull request. The final check is a green `s3-browser/ci/master` build of the merged sha, which Jenkins starts on the push; no `workflow_dispatch` or other run is started by hand, and nothing is pushed to `master` after that build starts. Releases are cut from the Jenkins job `s3-browser/release` (`Jenkinsfile.release` below), never from a workstation or a GitHub workflow.


- **Pushes to `master` are merges.** Nothing is committed to `master` directly: a push to `master` is the squash merge of a pull request, after the required `jenkins/gate` status was green on the pull request head (see *Working practice (Jenkins)* above).
- **Workflow permissions.** `macos-build.yml` declares `permissions: {}` at top level and `contents: write` on its one job, `build-macos`, and is dispatch-only, so no pull request can reach it. `codeql.yml` holds `security-events: write` on the one job that does not run for a pull request. The permission rule of section 3 (*Workflow permissions*) applies to every workflow file; `src/__tests__/ciWorkflowPermissions.test.ts` checks both files (and the validator's own red fixtures).
- **AppImage smoke test.** The last step of the `Release dry-run` stage and of `ci/release-build.sh` runs `scripts/smoke-appimage.sh` (default target: the one `release/*.AppImage`). It starts a container from the Playwright image `scripts/e2e-docker.sh` uses (`mcr.microsoft.com/playwright:v<version of @playwright/test in package-lock.json>-noble`), copies the AppImage in with `docker cp` (no host-path bind mount, so it also works from inside another container), extracts it with `--appimage-extract` (no FUSE needed) and launches the extracted `AppRun` under `xvfb-run`. It exits 0 only when a Chromium page titled `S3 Browser` (`S3B_SMOKE_TITLE`) appears and the process is still running 5 s later (`S3B_SMOKE_HOLD`); an early exit, no window within 60 s (`S3B_SMOKE_WAIT`) or a wrong title exits non-zero. The step comes after the electron-builder step. Electron flags the packaged app gets in the container: `--no-sandbox` because the container runs as root, where Chromium does not start its sandbox, and electron-builder's `AppRun` only adds it when its `unshare -Ur` probe fails, which never happens as root; passing it explicitly keeps the result independent of the runner's kernel; and `--remote-debugging-port=9222` so the script can read the window's title from `/json` without an X11 client tool (the image has none). No other flag is needed (the app starts with software rendering without `--disable-gpu`). `src/__tests__/repocheckCiLane.test.ts` asserts the stage's smoke call follows the electron-builder step, and `src/__tests__/runnerConfig.test.ts` that the script extracts the AppImage and uses `xvfb-run`, the Playwright image and `--no-sandbox`.
- **CI summary page.** The pure parsers and helpers live in `scripts/summary/jobSummary.ts` (no I/O) and the page renderer in `scripts/summary/summaryPage.ts`; `scripts/summary/summary.ts html [dir]` is the thin CLI the `Jenkinsfile` runs to write the page. It is the only mode: any other argument is a usage error (exit 2), and nothing is written to a GitHub job summary. `src/__tests__/jobSummary.test.ts` covers the parsers, the page and the CLI.

- **CodeQL (`.github/workflows/codeql.yml`).** The `CodeQL` workflow runs static analysis for language `javascript-typescript` with the `security-extended` query suite (`build-mode: none`), on GitHub-hosted `ubuntu-latest` runners only. Triggers: `push` to `master`, `pull_request` targeting `master` with `types: [opened, synchronize, reopened, ready_for_review]`, and a weekly `schedule` cron (Mondays 04:17 UTC). The workflow-level permission is `contents: read`; no job uses secrets. It has two jobs, because job permissions cannot be conditional. Job `analyze` has `if: github.event_name != 'pull_request'` (push and schedule), holds `security-events: write` at job level (the only place that permission appears in the file) and uploads the results to code scanning. Job `analyze-pr` runs only for a `pull_request` opened from this repository by `n-orlov` with actor `n-orlov` (the owner gate) that is not a draft (`github.event.pull_request.draft == false` in its `if:`; `ready_for_review` starts it when the draft is marked ready), has `contents: read` only, and runs `analyze` with `upload: never`, so code reachable from a pull request never runs beside a write permission. The repository's CodeQL default setup stays not-configured, since an advanced workflow conflicts with it. `src/__tests__/codeqlWorkflow.test.ts` parses the file and fails if a trigger (push to master, pull_request, weekly schedule) is missing, if the language or query suite differs, if a runner is not `ubuntu-latest`, if the top-level permissions grant write, if `security-events: write` is on anything but the single job that uploads, if that job's `if:` does not exclude `pull_request`, or if the pull-request job loses `upload: never`, the owner gate or the draft guard, or if the `pull_request` types list is not exactly the four above.
- **Dependency updates.** `.github/dependabot.yml` (version 2) has exactly two update entries, `npm` and `github-actions`, each at directory `/` with a `weekly` schedule and a group whose `update-types` are `minor` and `patch`, so minor and patch updates arrive as one grouped pull request per ecosystem and major updates arrive individually. The `npm` entry ignores `typescript` versions `7.x` (with a comment giving the reason): typescript-eslint 8.71.x peers `typescript <6.1.0` and the TypeScript 7 package exports no classic compiler API, so `typescript` stays on 6.0.x until typescript-eslint supports 7. `src/__tests__/dependabotConfig.test.ts` fails when an ecosystem, the weekly interval, the grouping or the typescript 7 ignore is missing.

- **macOS leg of the Jenkins release (`.github/workflows/macos-build.yml`).** The `macos-build` workflow is dispatched by the Jenkins release job (`workflow_dispatch` is its only trigger) to build the macOS assets from the release commit and attach them to the draft release Jenkins created; a draft has no tag yet, so it is addressed by its numeric id. Inputs, all required: `tag`, `sha`, `release_id` and `correlation_id`; `run-name` is `macos-build <tag> [<correlation_id>]`, so the dispatcher finds its run by the correlation id. Top-level `permissions: {}`; the one job, `build-macos` (`runs-on: macos-latest`, 30-minute timeout), holds `contents: write` and nothing else. The `concurrency` group `macos-build-<tag>` has `cancel-in-progress: false`, so two dispatches for one tag cannot race each other's uploads. Steps: validate the inputs (full 40-hex `sha`, numeric `release_id`, a `vX.Y.Z` tag), check out `sha` without persisted credentials, check through the API that release `release_id` is still a draft whose `tag_name` is `tag` and whose `target_commitish` is `sha` (otherwise fail), Node 22.x, `npm ci`, `npm run build` and `npx electron-builder --mac -p never` with `CSC_IDENTITY_AUTO_DISCOVERY: false` (the commands `Jenkinsfile.release` and `ci/release-build.sh` run for the other platforms), and an upload of every `release/*.dmg` with `curl` to `https://uploads.github.com/repos/$GITHUB_REPOSITORY/releases/<release_id>/assets?name=<file>` (spaces in a name percent-encoded; no dmg built is an error). It does not use `softprops/action-gh-release`, which looks a release up by tag and so cannot see a draft. `src/__tests__/repocheckMacosWorkflow.test.ts` asserts the trigger, the four inputs, the run-name, the empty top-level and the job-level permission, the runner, the draft check, the build commands and their order, and the upload by id, and is red for fixtures that add a `push` trigger, move `contents: write` to the top level, widen or drop the job permission, upload through softprops or by tag, drop an input, the draft check or the signing setting, or change the runner.

- **README badge row.** `npm run badges:readme` (`scripts/badges/readme.ts`; the pure generator is `scripts/badges/readmeBlock.ts`) rewrites only the block between the `<!-- badges:start ... -->` and `<!-- badges:end -->` comments at the top of `README.md`, and nothing outside them; running it twice leaves `git diff README.md` empty. - **Release build script (`ci/release-build.sh`).** Builds the release assets from one commit on an amd64 host: `ci/release-build.sh [--sha SHA] [--out DIR]` (default `HEAD`, `release-out`). The tree comes from `git archive` and goes into throwaway containers with `docker cp` (so it works inside another container), every `docker create` carries `--memory $BUILD_MEMORY` (default `3g`), and every container is removed on exit. In `node:22` it runs `npm ci`, `npm run build`, `npm run sbom` and `npx electron-builder --linux AppImage --x64 -p never` (`--x64` explicit, so the result never depends on the host's architecture); then `scripts/smoke-appimage.sh` runs on that AppImage (`S3B_SMOKE_DOCKER_ARGS="--memory $BUILD_MEMORY"`); then, in `electronuserland/builder:wine`, `npx electron-builder --win nsis portable --x64 -p never`. The output directory receives exactly `S3 Browser-<v>.AppImage`, `S3 Browser Setup <v>.exe`, `S3 Browser <v>.exe` and `sbom.cdx.json`; a failing smoke test stops the script before the Windows build. `src/__tests__/releaseBuildScript.test.ts` asserts `--x64`, the smoke call after the AppImage build, the targets `nsis` and `portable`, the sbom step, the memory caps and the four collected names, and is red for fixtures without `--x64`, without the smoke call, without either Windows target, without the sbom step, without `--memory` and with the smoke test before the build.
- **Release stage script (`ci/release-stage.sh`).** The GitHub half of the Jenkins release, run one phase per pipeline stage (`ci/release-stage.sh check|draft|macos|verify|publish|cleanup`, no argument = every phase in one process) inside `withCredentials` with `GH_TOKEN` set and tested by `src/__tests__/releaseStageScript.test.ts` against a stubbed GitHub client (`curl`) on `PATH`. The phases share the draft id through `$STATE_DIR/state.env` (required for a single phase); `publish` refuses to run unless `DRY_RUN` is set explicitly, and `cleanup` deletes the draft unless the release was published (it never touches a published release). Inputs (environment): `REPO`, `VERSION` (`vMAJOR.MINOR.PATCH[-pre]`), `RELEASE_SHA` (full sha), `DIST` (the `*.AppImage` and `*.exe` to upload) and optionally `SBOM` (default `$DIST/sbom.cdx.json`), `SOURCE_DIR`, `DISPATCH_REF` (default `master`), `MAC_TIMEOUT_MIN` (default 45), `DRY_RUN` (default `false`). Before anything exists on GitHub it refuses (non-zero, no draft created) when the tag exists, when a release or draft already carries the tag, when `package.json`'s version differs from `VERSION` without the `v`, or when `GET /immutable-releases` is not enabled. It then creates the draft with `POST /releases` (`draft: true`, `target_commitish` the sha, `prerelease` for a `-pre` version) keeping the numeric id, uploads the assets and `sbom.cdx.json` by that id to `uploads.github.com`, dispatches `macos-build.yml` with `return_run_details: true` (falling back to a lookup by the `[correlation_id]` in the run name), checks the run's title carries the correlation id and polls it until `completed` or the deadline (then it cancels the run). A run that does not conclude `success` fails the script. In the single-process mode an `EXIT` trap deletes the draft by its id on any failure before the release is published; stage by stage the pipeline's `post { failure }` and `post { aborted }` call `cleanup` for that. After the macOS leg it verifies the draft (`GET /releases/<id>`): the assets must be exactly `S3.Browser-<v>.AppImage`, `S3.Browser.Setup.<v>.exe`, `S3.Browser.<v>.exe`, `S3.Browser-<v>.dmg`, `S3.Browser-<v>-arm64.dmg` and `sbom.cdx.json` (GitHub's dotted names), each in state `uploaded`; a missing, extra or unfinished asset fails the script and the trap deletes the draft. With `DRY_RUN=true` the verified draft is then deleted and nothing is published (no `draft=false` PATCH). Otherwise it publishes with `PATCH /releases/<id>` `{draft: false, prerelease, make_latest}` (a `-pre` version is a prerelease with `make_latest: "false"`), marks the release as published so the trap never deletes it, checks that `git/ref/tags/<VERSION>` points at `RELEASE_SHA` and that a re-read of the release shows `immutable: true` (polled briefly, since GitHub seals it a moment after the publish); either miss exits non-zero with the release left in place. Every call sends `X-GitHub-Api-Version: 2026-03-10`; JSON is read with `python3`, so the agent needs `curl` and `python3`, not `gh` or `jq`.
- **Release pipeline (`Jenkinsfile.release`, job `s3-browser/release`).** A pipeline job started by hand, running the file from `master` on `agent { label 'amd64 && docker && s3-browser' }` (int21h-ws), with `skipDefaultCheckout()`, `disableConcurrentBuilds()` and parameters `VERSION` (validated as `vMAJOR.MINOR.PATCH[-pre]`), `CI_BUILD` (a build number) and `DRY_RUN`. Stages, in this order: `Candidate` (`copyArtifacts` of `release-candidate.json` from `s3-browser/ci/master` with the `lastSuccessful(stable: true)` selector, or `specific(CI_BUILD)` when `CI_BUILD` is set; a build that was not green has no such file, so the copy fails and no later stage runs), `Checkout` (`checkout scm`, check that the candidate sha is an ancestor of `master`, then `git checkout --detach` at the sha read from the file, never `master`'s tip), `Version check` (`ci/release-stage.sh check`), `Build` (`ci/release-build.sh --sha "$RELEASE_SHA" --out dist`, 40-minute timeout), `Draft` (`ci/release-stage.sh draft`), `macOS` (`ci/release-stage.sh macos`, 60-minute timeout), `Verify` (`ci/release-stage.sh verify`) and `Publish` (`ci/release-stage.sh publish` with `DRY_RUN` set from the parameter in the stage's `environment`: a dry run deletes the verified draft instead, otherwise the draft is published and the tag and `immutable: true` are read back). Every GitHub call runs in `withCredentials` (`github-n-orlov`). `post { always }` archives `dist/*` and writes the build-page summary (`currentBuild.displayName`/`description` and `addSummary` with the version, the candidate sha, a link to the `s3-browser/ci/master` build and the release link or "dry run"); `post { failure }` and `post { aborted }` run `ci/release-stage.sh cleanup`, which deletes a draft that was not published; `post { cleanup }` calls `notifyTelegram` (with a sound, inside `try/catch`: delivery is best-effort and never changes the result). The candidate comes from `Jenkinsfile`: in `post { success }` of a `master` build only (`env.BRANCH_NAME == 'master'`), before `jenkins/gate` turns green, `archiveReleaseCandidate()` writes and archives `release-candidate.json` with `job`, `build` (number) and `sha`, so a green master sha always has one and a red or PR build never does. What stays on GitHub: the repository, the tag and the release itself (created as a draft and published by the REST API with the job token, which Jenkins reads back for `immutable`), CodeQL, Dependabot, branch protection (required status `jenkins/gate`) and the `macos-build` workflow that builds the two dmgs on a macOS runner. `src/__tests__/repocheckRelease.test.ts` asserts the stage order, the parameters, the agent labels, the candidate selector, the checkout of the candidate sha, the archive in `post { success }` for master only, the draft deletion in `post { failure }` and `post { aborted }`, the `DRY_RUN` guard on `Publish`, the immutable read after the publish and the `notifyTelegram` call in `post`, and is red for fixtures selecting `lastCompleted()`, checking out `master` or `scm` instead of the candidate sha, archiving in `post { always }`, dropping the draft deletion, dropping the `DRY_RUN` environment and reading `immutable` before the publish.
